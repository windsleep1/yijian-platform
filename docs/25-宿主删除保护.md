---

## 0. 一句话

**应用不删。**

会被宿主的删除保护拦的删除，**一律 `rename` 到 `.trash/`**，由**宿主或人**回收。
唯一允许"直接删"的形态 = **单文件 + 非递归**，**且必须登记**（`trash-ok: <理由>`）。

---

## 1. 机制：宿主的删除保护到底拦什么

**判据（唯一的那一条）**：**这次删除会不会被拦？**

拦截条件 = **单轮累计 > 50 项**。坑 62 记的细节很关键：

```
SAFE_DELETE_BULK_CONFIRM_REQUIRED {count:247, threshold:50, targets:[".coverage.cli"]}
                                   ↑ 已用额度（按轮累计）        ↑ 本次要删几个
```

- `count` 是**这一轮已经用掉的删除额度**，不是本次要删的项数；
- ⇒ **前面删过东西，会让后面那次"只删 1 项"也被拒**（坑 62 的原形：先手工删 `htmlcov/` 吃掉 55 个额度，
  后面 `coverage combine` 就被堵死了）。

**推论（方案的全部依据）**：

| 形态 | 项数 | 判据 | 处置 |
|---|---|---|---|
| **目录 / 递归 / 通配** | **不可预知** | 会拦 | **一律 rename**（**不许"我猜它很小"** —— 坑 62 就是猜错的代价） |
| **单个文件** | 1 项 | 不会拦 | **可以直删**，但**必须登记** |

> ★ 为什么"目录一律 rename"而不是"我确认它很小就删"：
> 那正是把**可判定的判据**（形态）换成**不可判定的判据**（大小估计）。
> 硬约定 R 与 P 同族：**模糊规则 = 给执行者留后门。**

## 3. 三层处置

### A. 我们自己的删除 → **改 rename**

一行搞定，别手写 `p.rename(...)`：

```python
import trash                      # tools/local-verify/trash.py
trash.trash(p, kind="coverage")   # → <repo>/.trash/coverage/<name>[.N]
```

**为什么要有那个模块，而不是各处自己 rename**：一个名字只有一个来源。
`.trash/<kind>/` 的布局有 **4 处**调用点（`e2e-web.py` / `run-local-pipeline.py` 走 `trash.py`；
`preflight.sh` / `run-smoke.ps1` 直接写路径 —— 见 §8 那条残留风险），各写一份必然漂移；
而漂移的后果是**某个角落里的旧产物没有任何清理机制能看到**（它不占门禁、只占磁盘 ⇒ 不会报错，只会把盘填满）。

`rename` 是**元数据操作**：不触发守卫、瞬时完成、同盘无数据拷贝。

### B. 第三方的删除 → **我们改不了 ⇒ 只能绕**

| 手段 | 实例 | 代价 |
|---|---|---|
| 让目标**不存在** | `isolate_next_dir()` 在 `build`/`dev` 之前把 `.next` rename 走 | 会积累（进 `.trash/next/`） |
| **别在本机做那件事** | 产物构建归 CI 的 `web · build`（本机只跑 `--e2e-dev`） | 本机不再验产物 |

### C. 单文件 → **登记制**

```python
# trash-ok: 单文件（PG 的 pid 文件），非递归
(self.pg_data / "postmaster.pid").unlink(missing_ok=True)
```

- 登记可以写在**同一行尾部**，或**上一行**、且那一行**只有注释**；
- **为什么允许上一行**：代码行常常已经贴着 100 列，再往后接理由会**为了写登记而破格式**，
  而格式红线本身是另一道门禁 —— 两条约束不该打架；
- **为什么只认"独立注释行"**：`x = 1  # trash-ok` 这种带代码的不算，
  否则登记会被一个"顺手的说明"满足掉，退化成噪音。

登记不是"免死金牌"，它买的是**可见性**：一次运行就能把全部豁免列出来（见 §6）。

## 4. `.trash/` 的布局

**唯一来源** = `tools/local-verify/trash.py`（`KINDS` 是白名单 —— 随手传一个新 kind
会在回收站里长出一个"没人知道该不该清"的目录）。

| kind | 谁产生 | 内容 |
|---|---|---|
| `.trash/next/` | `e2e-web.py::isolate_next_dir` · `preflight.sh::prepare_tsc_input` | 旧 `.next` / 陈旧 `.next/types` |
| `.trash/coverage/` | `run-local-pipeline.py::_retire` · `run-smoke.ps1` | `.coverage*` / `coverage.xml` / `htmlcov/` |
| `.trash/chrome/` | （预留给 CDP） | —— |
| `.trash/misc/` | 兜底 | —— |

`.gitignore` 必须有 `.trash/`（不变量 6 会查）。**在 `%TEMP%` 下的两处**（Chrome 的
user-data-dir、`test-cov-clean.ps1` 的夹具）挪到 `%TEMP%` 的兄弟目录，由 **OS** 回收。

## 5. `preflight` ⓿ 与 R 的分工（**别把这两件事混起来**）

| | **R** | **⓿** |
|---|---|---|
| 管什么 | **应用怎么删** | **清残留**（卫生） |
| 手段 | 一律 `rename` 进 `.trash/` | **单文件**直接回收 + **目录只报告** |
| 错了会怎样 | 产物永远清不掉（占盘） | 只是少清了一点 —— 它**不是门禁**，不进退出码 |

⚠️ **⓿ 不是"应用可以删"的豁免。** 它自己**也要**守 R：它删的**只有单文件**
（`find … -maxdepth 1 -type f`，每个 1 项），**目录一律不动手**。

**为什么 ⓿ 不再 `rm -rf`**（2026-09-29 改）：拦的是"单轮累计 > 50 项"，
一次 100~300MB 的 `.next` 必然远超 ⇒ **那条 `rm -rf` 从来没有成功过**。
它唯一的作用是让"验收测试"在**小探针**上变绿 —— 这正是**假绿**
（硬约定 H：**验收脚本本身也要被验收**；"测试过了"与"产品能力变了"是两件事）：

> 上一版的验收写的是"10 天前的**探针**被清、刚建的保留、rc=0"。
> 探针只有几项 ⇒ 删得掉 ⇒ 绿。**真负载（47MB / 125 项）从来删不掉。**

⇒ 现在它报的是**真相**：哪些目录占着、总共多大、要回收请在自己的终端里跑那一条命令。

## 6. 物理约束：不变量 6

`python tools/local-verify/check-invariants.py` 的第 6 组（CI 的 ② 步骤自动覆盖）。

- **扫**：`tools/` `apps/` `packages/` `db/` `deploy/` 下的代码（`.py .sh .ps1 .js .mjs .cjs .ts .tsx`，
  外加**显式列出的** `Dockerfile` —— "没扫"是一个**静默漏洞**，没人会问"为什么它不在范围里"）；
- **不扫 `.md`**：`docs/` 里有大量 `rm -rf` 的**示例**，算成违规就是**假红**，
  而假红的下场是被加豁免或干脆删掉（硬约定 J）；
- **先剥注释与三引号块**（词法级，**不 import `ast`** —— 这个脚本必须纯标准库），
  否则 `run-local-pipeline.py` 的 docstring 里那句给运维看的手工命令会把门禁变成恒红；
- **整路径豁免**写在 `PATH_EXEMPT` 里（一处可审完，**不散在代码注释里**），目前只有
  `apps/api/Dockerfile`（在**容器镜像内**执行，碰不到宿主文件系统）；
- **变异验证**：`mutate-invariants.py` 往一个被扫到的文件里塞一行未登记的
  `shutil.rmtree` ⇒ 必须变红（当前 **5/5 捕获，0 未应用**）。

**当前状态**（2026-09-29）：扫描 **237** 个代码文件 / **23** 处登记豁免 / **1** 条整路径豁免。

## 7. 加一个新的"删除点"时怎么办

1. **先问形态**：目录 / 递归 / 通配 → 走 A（`trash.trash(...)`）；
2. 只有**单文件 + 非递归**才考虑 C（登记），且理由要**能被审**（写"它是 1 项"，不要写"应该没事"）；
3. 跑 `bash tools/check-invariants.sh` —— 没登记的一律红；
4. 如果你正在绕一个**第三方**的删除 → 走 B，并把"绕法 + 代价"写进本节或 `docs/24`。

## 8. 残留风险（如实记，不假装方案是完备的）

- **跨盘 / 被占用**：`trash()` 会抛 `OSError`（**不"退化成删除"**）。调用方必须自己决定
  "报错"还是"可以忽略" —— 已经这样处理的两处都写了理由（覆盖率清场：报出来；
  Chrome profile：忽略，因为它是纯卫生问题，**不能让清理失败伪装成 E2E 挂掉**）。
- **shell / PowerShell 两处拿不到 `trash.py` 的常量**，只能直写 `.trash/<kind>/` 的路径
  （`preflight.sh::prepare_tsc_input`、`run-smoke.ps1` 的 htmlcov）。
  ⇒ 这是本方案**唯一的"一个名字两处来源"**。缓解（一条命令，3 行输出）：
  `grep -rn '\.trash' tools/ apps/` —— 新增调用点必须在这里出现，且**必须**用 `next/coverage/chrome/misc` 之一。
  （不做成自动门禁的理由：把"允许写这个字符串的文件清单"也变成登记表，会让加调用点这件事变贵，
  而收益只是防一个 4 处的漂移。）
- **`%TEMP%` 下的回收站**（Chrome profile、测试夹具）交给 OS，**没有人看着它**；
  它们的量级是单次几十 MB 且随系统清理 ⇒ 风险可接受，但不是零。
- **`check-invariants.py` 自己的 token 表**必须靠"上一行登记"绕开自己 ——
  这是自指问题的必然代价。缓解：那条登记的文字明确写着"这是判据的定义处"，
  一个**真**加进去的删除不会长得像它。
- **`tools/` 至今没有格式门禁**（`ruff format --check` 只覆盖 `apps/api`，BL-10）——
  本方案不改变这一点（`tools/` 目前有 18 个文件未格式化，属已知欠账）。
- **`.coverage-trash/`** 是历史名字，已并入 `.trash/coverage/`；`.gitignore` 里那条**只作保险**。
