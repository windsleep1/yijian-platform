**症状**：PWA 里**选完科目永远建不出练习**（章节列表恒空，页面显示「这门科目还没有章节」）；
同族：`toggleFlag` 用 URL 的**字符串** qid 查 `idbGet("questions", qid)`，而库里的 id 是**数字** ⇒ 标记 / 收藏一律 `40401`。

**根因**：`importBank` 把包里的 JSON id **原样写库**（数字），而 URL 段 / 查询串给的是**字符串** ⇒
`c.subject_id === sid` 这类**严格比较恒为假**。实测对照：`=== String(s0.id)` → **0 条**；`=== s0.id` → **3 条**。
★ 已排除精度（id 最大 9 位 ≪ 2^53）；★ `types.ts` 声明 `id: string` —— **类型是假的**（不变量 8 的反例）。

**修法**：**在边界上统一形状**（`asId()` 唯一转换点 + `normalizeIds()` 按名字认 id 字段），**不在比较点打补丁**。
**判据两处，各管一半**：**静态** = 不变量 14（`seg[n]` / `query.get("<…id>")` 必须在 `asId(` 里）；
**行为** = 走查器 `setup` 的 **③b**（读库断言 id 全是字符串）。
★★ **静态只能证明"代码走了 `asId`"，行为才能证明"写进库的真的归一了"** —— 这句是本批最值钱的一句。

★ **口径澄清（免得当成两个缺陷）**：「`marks` 场景跑出来的选科建不出练习」与「P0 的 id 归一」
**是同一件事** —— 同一根因（同一字段两种写法）的**两个症状**：
① `listChapters(seg[1])` 拿 URL 的**字符串**筛 `c.subject_id`（库里的**数字**）⇒ 章节列表恒空；
② `toggleFlag` 拿 URL 的**字符串** qid 去 `idbGet("questions", qid)`（主键是**数字**）⇒ 标记/收藏 `40401`。
⇒ 修复是**一处**（导入边界 `normalizeIds`），不是两处；本报告 §0 的"P0 修复 1 个"说的是**这个**。

### 3.2 ★★ 判据自身的缺陷：**UI 会把"库里的事实"盖住**（`notes` 场景挖出来的）

### 3.3 ★★ 一条**被自己推翻的**判断："拿不到" ≠ "没实现"

| **登录 / 用户体系** | C 端 `lib/auth-store.ts` + **11 个文件**触及 `auth\|login\|token`；PWA 只剩 **5 个**且**逐条判读**为注释 / 类型声明 / 一个恒返回 `false` 的哑桩（判据 7） |
| **多设备**（用户态在服务端） | C 端用户态经 API 存取；PWA 的用户态**只在这台机器的 IndexedDB** |
| ★ **答案不下发** | C 端由服务端判分 ⇒ 考前拿不到答案；PWA **必须**把答案存本机才能离线判分（`docs/32` 已写明：那条保证在 PWA 里**只是界面级**的） |
| ★★ **`json-bigint.ts` 精度安全带** | C 端与 `apps/admin` **同源各存一份**（`parseJsonSafe` + `looksLikeUnsafeId`），抬头写着"主路径是后端把 ID 序列化成字符串（`BigIntStr`），本文件是**防御垫**"；`types.ts` 还写着"前端**任何地方都不许**对它 `Number()`" |

### 8.2 PWA 有、C 端没有

| 项 | 证据 |
|---|---|
| **离线**（Service Worker + IndexedDB） | `docs/28` / `apps/pwa` 的 SW；数据层整个换成 IndexedDB |
| **零后端成本** | 无服务器、无数据库、无账号 |
| ★ **没有 user 概念** | 判据 7：零身份泄漏（参数与过滤条件 **0 处**）—— 这是"单机"换来的**红利** |
| **数据备份 / 导出** | `/me/backup`：先看 → 再问 → 才写；`bank_matches=false` 时禁用确认 |
| **自带全量题库** | 导入 6000 题 **0.51s / 5.99 MB**，不依赖网络 |

### 8.3 两边"共同踩"的——★ 但**只有两条是共同踩，第三条不是**

| 项 | 结论 |
|---|---|
| **成对判据**（二元对立必须成对验） | ✅ **真·共同**：C 端批次 2/3 就这么做的，PWA 每个场景都配了对照（`marks` ⑤ / `fav` ⑥ / `loop` ⑦b） |
| **"UI 盖住库"** | ✅ **真·共同**：C 端批次 3 的可证伪锚就是"**编辑后条数仍为 1**"（拦"编辑其实插了一条"）；PWA `notes` **复现**了它，并把判据**升级**成"**库里的行数 == 1**"（§3.2）—— 因为实测发现**面板会被内存态盖住**，只看 UI 根本看不出来 |
| ★★ **id 归一** | ❌ **不是"共同踩"，而是"同一条规则在新边界上被漏掉"**：C 端（+ admin）**早就有** `json-bigint.ts` 这道垫子、`types.ts` 也写着"不许 `Number()`"；而 PWA 的**边界换成了 IndexedDB** ⇒ `parseJsonSafe` 对它**不适用**，**对应的垫子（写库前归一）却没做** ⇒ P0 爆在 PWA。<br>★ 而且 PWA 的 id **≤ 9 位**（**不涉精度**）⇒ 同一个**规则**（不变量 8「一个字段只有一种写法」）、完全不同的**机制**。<br>★ `docs/24` §2 已裁定"共享包只装两端**必须逐字一致**的三件事"⇒ 防御垫**有意不进包** ⇒ PWA **本来就需要自己的对应物**（`normalizeIds`），只是**没人把它和 C 端那条规则挂上钩**。 |

★ 顺手核了一条"看起来 PWA 少做了"的：**报告页的笔记计数** —— `grep -c` 在
`apps/web/.../report/page.tsx` = **0**、在 PWA 同页也是 **0** ⇒ **两边都没有**，不是 PWA 少做（`notes` 场景里如实记为"5 条读路径里第 4 条**不存在**，不写断言、也不算查过"）。
