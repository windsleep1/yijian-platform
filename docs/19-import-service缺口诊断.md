## 0. 一句话结论

109 条未覆盖里 **没有一条是死代码** —— 每个函数都有调用点，每条分支在逻辑上都有触发条件。
缺口全部来自**"有实现、但没有人为它构造输入"**。

但有一条结构性发现，决定整批怎么做：

> **109 条里有 78 条（72%）只需要两个函数入口就能拿到 —— `parse_file` 与 `validate_row`，
> 而且不必直接测任何私有函数。**

这意味着这批的主体可以**不依赖 DB、不依赖 API、不依赖任何 fixture**：
一条测试就是"给一个 dict / 一段字节，断言返回值或异常"。

## 2. ★ 核心发现：两个入口吃掉 78 条

| 入口 | 类型 | 条数 | 覆盖哪几组 |
|---|---|---|---|
| `parse_file(content, file_type)` | **纯函数**：文件字节 → 行字典列表 | **15** | §3.1 输入解析容错 |
| `validate_row(row, row_no, ctx)` | **纯函数**：行 + 上下文 → `RowOutcome` | **63** | §3.2 / §3.3 / §3.4 |
| 其余（需文件系统 / DB / HTTP） | | **31** | §3.5 – §3.10 |

> 补一句口径：§3.5 里的 `_read_batch_file`(1411) 与 `_stored_file_size`(1419/1420) 只需**文件系统**、
> 不需要 DB/API，可以在进程内直接调 —— 所以**完全不碰 PG 的是 81 条**（78 + 3），
> 真正需要 DB 或 HTTP 的是 **28 条**。

**为什么这很重要（两条）**

1. **成本**：78 条不需要 PG、不需要起 API、不需要现成数据。`ValidationContext` 是普通 dataclass
   （字段都是 dict/set），**可以手工构造** —— 不必走 `load_context` 的四条 SQL。
2. **不违边界**：`_s` / `_int_or_none` / `_float_or_none` / `_decode_text` / `parse_answer_points` /
   `_build_answer` **全是私有函数** —— 直接测它们会在"重命名 / 内联 / 拆分"时变红，
   正违反"重构实现但不改契约时不该红"的判据。
   而这 78 条**全部能经两个公开入口间接覆盖**（下面逐条标了入口）。

⚠️ 一处需要说明：`parse_file` 不是对外 API 契约，但它是**导入管道唯一的"文件 → 行"接口**
（`create_batch:640` 与 `_load_full_payloads:1365` 都调它）。测它的"输入 → 输出 / 异常"是合理的契约测试。

## 5. 一处需要判断的"第二道防线"

`execute_batch:1242` 与 `_load_full_payloads:1363` 抛的是**同一条错误**（"批次原始文件已不可用，无法执行导入"）：
1242 在 execute 早期检查，1363 在更后面（重新解析原文时）**再查一次**。

- 删文件 → **1242 先抛** → 1363 **在正常流程里到不了**
- 要覆盖 1363，只有两条路：① 进程内直调 `_load_full_payloads`（需要 DB session + batch dict）；
  ② 构造"1242 通过之后文件才消失"的并发窗口

**建议**：1363 属于"同一守卫的第二道"，**保留代码、暂不补测**，在本批记录为
"已知未覆盖的防御性重复"。若要求严格覆盖，走 ①（成本中等）。
