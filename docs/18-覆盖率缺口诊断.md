### 1.1 边界 #1 的实测证据（同进程、只改一个变量）

`tools/local-verify/_probe_greenlet.py` 用 ASGI 直驱（不经 uvicorn），
只改 `concurrency`，测两处**必然执行**的行：

| 配置 | `auth.py:76`（注册路由 return） | `deps.py:117`（取权限） | `deps.py` 90-130 覆盖行 | `auth_service.py` 覆盖行数 |
|---|---|---|---|---|
| 默认 `thread` | ❌ False | ❌ False | `…111,` **`121`**, `124` | 119 |
| **`greenlet`** | ✅ True | ✅ True | `…111,` **`112,114,117,118`**, `121,124` | **181** |

判据来源：用例断言的**就是** `auth.py:76` 的返回值；`deps.py:117` 在 `current_user` 里，
每个带鉴权的请求都要跑。**它们不可能没执行。**

注意那张表的形状 —— 这是根因的指纹：

```
deps.py:111  ✅ 有记录   ← 第一个 await（切栈**之前**）
deps.py:112-118 ❌ 全丢  ← 切回来之后，追踪器的"当前帧"已经指错
deps.py:121  ✅ 有记录   ← 模块级，另一个帧，不受影响
```

**为什么排错绕了远路**：默认 / `pytrace` / `ctrace` 三种追踪内核结果**完全一致**，
说明问题不在"用哪个内核"，而在"内核与 greenlet 栈切换没有对接"。
排错顺序的教训记在 `apps/admin/docs/B端联调坑.md` 坑 54。

⚠️ 还有一个容易漏掉的性质：**旧数据不是"偏低"，是"偏错"**。
`auth.py` 在旧口径下覆盖 **93** 行、新口径 **78** 行 —— 同样三个请求，
旧口径**多记了 15 行没执行的分支**。也就是说旧数字**两个方向都错**，
它既不能用来定门槛，也不能用来判断"哪里有缺口"。

### 1.2 边界 #2 / #3 的规模是"测出来的"，不是估的

- **#3**：把 `tests/test_idgen.py` + `test_admin_v4.py::test_content_hash_and_answer_derivation`
  在 pytest 进程里跑一遍，再合并两份数据 → **579 → 555（−24）**，
  其中 `core/idgen.py` 一条文件就 **28 → 6（−22）**。其余 20 个文件**一条不变**，
  这反过来证明"HTTP 用例确实都打在 API 进程里"，边界很干净。
- **#2**：`cli.py` 是 190 语句单文件 100% 缺失，占**全部缺口的 33%** ——
  这是目前**单笔最大的**账。

测试可以直接传一个会抛异常的替身 —— 这属于构造输入，不属于改环境。
