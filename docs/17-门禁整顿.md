# 17 · 门禁整顿（方案与验收）

> 批次：**门禁整顿**（2026-09-20）。拆三步走，每步**独立可验收**：
> **第一步**（真门禁能跑）→ **第二步 Commit A**（逻辑：清存量 + 提级 + 覆盖率）→
> **第二步 Commit B**（纯格式：prettier + ruff format）。
>
> 之后是**补测批**（专攻 `services` 层覆盖率），本文件末尾记了它的范围与触发条件。

## 0. 为什么会有这一批

门禁在整顿之前**有两道是假的**：

| 假门禁 | 表现 | 根因 |
|---|---|---|
| `npm run lint` | 脚本在、**配置不在** | 仓库里没有 eslint 配置、`eslint` 也不在 devDependencies → `next lint` 进**交互式提问**，CI 里直接卡死。它"跑得动"只是因为它从来没真跑过（坑 44） |
| `run-smoke.ps1` | 本地一直绿 | **不灌题库种子**，而题库落在 gitignored 的 `data/`。全新库上 **32 failed** —— 它绿只因**开发机的库早先被手工灌过**（坑 51） |

两者同族：**给的是"通过"而不是"失败"，且只在"环境恰好脏"时成立**。
判据就是硬约定 H —— **把 `node_modules` / 数据库 / 缓存全删掉，它还能不能绿？**

`ruff` 当时是第三道：配置和依赖都没有，`ruff check` 在 CI 上会直接 command not found。

## 1. 第一步：让真门禁能跑（已交付）

- `apps/admin/.eslintrc.cjs` + eslint 工具链（`@typescript-eslint` 基础集 + `react-hooks`）
  —— 规则**先全设 warn**，把清单露出来
- 仓库根 `ruff.toml` + 把 `ruff` / `fakeredis` 写进 `apps/api/requirements.txt`
  （之前只在本地临时装过 → CI 上找不到命令）
- `.github/workflows/ci.yml`：push `main` + PR，两个 job（后端 / 前端）
- `npm run lint` 清单 **14 条**；`ruff check` 清单 **19 条**（含 1 个真 bug）

### 「第一步完成」的三条标准（现在全满足）

1. 本地 `run-smoke.ps1` **从零库可复现全绿**
2. `ruff check` 是**拦截式**
3. CI 每次 push 都跑**"全新环境"路径**

### 这一步的两个副产品

**① ruff 第一次跑就抓到真 bug**：`test_admin_v3.py` 用了 `pytest.skip(...)` 但**没 import
`pytest`**，而被 `if _dsn() is None:` 包着 —— **只在 `DATABASE_URL` 未设时才炸**，
所有环境都设了它 → 测试全绿、`compileall` 也过，纯潜伏地雷。

**② CI 第一次 dry run 就抓到假绿**（坑 51）：见上表。
修法不是"在 CI 里补一段 SQL"，而是**抽成 `tools/local-verify/seed-questions.py` 单一实现**，
`ci.yml` 与 `run-smoke.ps1` **调同一个脚本** ——
两边各写一套的话迟早漂，于是又回到"本地绿、CI 红"的口径分歧（**正是坑 51 本身**）。

## 2. Commit A：逻辑改动（已交付 `6f64efd`）

| # | 内容 | 结果 |
|---|---|---|
| 1 | eslint 14 条存量清零 | `No ESLint warnings or errors` |
| 2 | eslint warn → **error**（并挂上 CI） | 变异验证：造一条违规 → 退出码 **1** |
| 3 | `app/cli.py` 控制台输出改**纯 ASCII**（硬约定 I） | 29 处；自查非 ASCII 输出行 = 0 |
| 4 | **覆盖率门禁** | 门槛 `65`（首次实测 65.64%） |

### 4 的细节：覆盖率必须量在 API 进程里

用例是**通过 HTTP** 打到独立 uvicorn 的（`conftest.py` 里就是个普通 `httpx.Client`）。
所以 `pytest --cov=app` 只能量到测试自己导入的几个纯函数模块 ——
**业务代码全跑在 API 那个进程里，就得在那里采**。

**并且**收尾不能用 `Stop-Process -Force`（硬杀 → `atexit` 不跑 → 数据一个字都写不出来，
而报告会把"没有数据"显示成 **0%** 而不是报错）。加了 `--shutdown-file` 哨兵 +
两处硬断言（数据文件非空、日志里必须有 `[cov] data saved`）。

**门槛只有一个来源**：仓库根 `.coveragerc` 的 `fail_under`；`run-smoke.ps1` 与 CI
都不在命令行重写数字。

### 一个被改掉的口径（留记录）

用户原本要求「实测值 +5~10%」（65.64 + 5.4 ≈ **71%**）。但 **71 > 65.64** ——
门槛一落地就必然恒红，`run-smoke` 不再全绿、CI 白不起来。
**两条要求在数学上不能同时成立**，于是按「**恒红的门禁等于没有门禁**」（硬约定 H）
取了"门禁必须真能跑"，把门槛定在**实测值下方一点点**当棘轮。

用户随后裁定**接受 65%**（承认当时表述不严谨），并要求补两个机制 —— 见下 §4。

## 3. Commit B：纯格式（已交付）

| # | 内容 |
|---|---|
| 1 | `prettier`（前端）：54 文件 |
| 2 | `ruff format`（后端）：35 文件 |
| 3 | CI 加 `npm run format:check` + `ruff format --check`（均**拦截式**） |
| 4 | `.gitattributes`（`* text=auto eol=lf`） |
| 合计 | **90 文件 / +3638 −1631** |

### 格式化的两个决定（都不是默认值）

**① 行宽 100**（prettier 默认 80、ruff 默认 88）。依据是实测：

```
apps/admin/src  17537 行 → p95=79  p99=100   超过 80 列 4.7%   超过 100 列 0.9%
apps/api        17623 行 → p95=83  p99=97    超过 88 列 2.9%   超过 100 列 0.5%
```

取 100 只要碰 0.5%~0.9% 的行。**格式化的第一原则是"别让 diff 里混进样式噪音"** ——
这个 commit 的 diff 本来就有几千行，再叠上"我喜欢的风格"就彻底读不出真变化。

**② Markdown 与 `docs/` 被 `.prettierignore` 排除**：那是手写文档，表格靠手工对齐、
列表按语义断行、代码块里的输出原样抄 —— 格式化它们**不带来工程收益**（没有编译器读它），
只会产出几百行无信息量的 diff。prettier 只管代码与配置。

### 语义等价性验证（这一条比"检查通过"更硬）

- **后端**：把格式化前后两份源码都 `ast.parse` 再 `ast.dump` 逐字节比对 ——
  **52 个文件 AST 完全一致** → 零语义变化（比"测试通过"强：测试只覆盖跑到的路径）
- **前端**：`next build` **成功**（14 条路由全构建）+ `tsc --noEmit` + `eslint` 均干净
- **回归**：`run-smoke.ps1` **从零库**（先 `DROP DATABASE`）→ `126 passed, 1 skipped`、exit 0

### `.gitattributes` 为什么"零成本"

本机 `core.autocrlf=true` → "工作区 CRLF、index LF"。加之前核对：
**index 里 208 个文本文件本来就全是 LF**，所以这个文件没有产生任何 renormalize 差异
（`git add --renormalize .` 后 `git status` 无新增）。它只是把这个事实**固定下来**。

### ⚠️ Commit B 里有一处**不是格式**的改动（必须说明）

`apps/admin/components.json` 顶部原有一段 `<!-- -->` HTML 注释 ——
**HTML 注释既不是合法 JSON、也不是合法 JSONC**，于是这份配置对它自己的用途
（shadcn CLI 用 `JSON.parse` 读它）**是坏的**。是接入 prettier 时解析报错才发现的
（`Unexpected character '，'`）。

处理：改成纯 JSON，把说明搬到 `apps/admin/README.md`。
**它是"纯格式"提交里唯一的内容改动**，理由是"不修它 prettier 就跑不起来，门禁挂不上"。
单独记为坑 53。

### 「可选：pre-commit hook」——本批**没做**，理由

`husky` + `lint-staged` 会往 `.git/hooks` 装东西，而**本仓所有门禁都已经在 CI 上拦截**，
本地再挂一层只省一次 push 往返。而它的成本是：多两个依赖、多一层"钩子没装成功就静默跳过"
的失败模式（**正好是这一批在治的病**）。
真要提效率，更直接的做法是把 `npm run lint && npm run format:check && ruff check`
写进一个 `npm run gates`，想要的人自己跑。**本批不做，记为待办。**

## 4. 门槛的两个"防僵化"机制（用户裁定后补的）

**① `.coveragerc` 里写可判定的触发条件，不写"目标"**

```
触发：实测总覆盖率 ≥ 70%     或   services 层 ≥ 60%
动作：把 fail_under 改成 71
```

只写"达到后改成 71"依赖某个人的记忆，而**没有任何交付流程会因为"当时说过达到后要改"
而停下来** —— 结局就是门槛从"棘轮"退化成"一个数字"。

**② 收尾动作新增 §5「覆盖率数字对照（每批必看）」**
（`apps/admin/docs/B端联调坑.md` 末尾）—— 跑一次 `coverage report`，把数字与触发条件对照，
达标就本批抬。**棘轮只有"会动"才叫棘轮。**
