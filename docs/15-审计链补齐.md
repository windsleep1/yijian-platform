## 1. 问题：状态**能改**，但"谁改的、什么时候改的"从来没被记录

`docs/14` 审计时按硬约定 F 的判据（"读路径有判断 ≠ 该状态可达"，反向亦然）顺带查了
**审核/批改类配套字段的引用数** —— 结果是 **0**：

| 表 | 字段 | 全仓引用数 | 本该由谁写 |
|---|---|---|---|
| `questions` | `reviewed_by` / `reviewed_at` | **0** | 题目审核动作（`draft → published` 时的审核人） |
| `comments` | `audited_by` / `audited_at` | **0** | 评论审核动作（`pending → approved/rejected`） |
| `exam_attempt_items` | `reviewer_id` / `review_comment` / `reviewed_at` | **0** | 人工批改主观题 |

### 为什么这是个问题（而不是"字段先留着"）

**`questions.status` 的 5 个值全部可达**（创建/编辑接口都接受），
所以从"状态机完整性"看它是正常的 —— 但审核这件事在系统里**只体现为一个枚举值的变化**：

```
现在：  draft ──(PUT /admin/questions/{id} 改 status)──→ published
        没有审核人、没有审核时间、没有审核意见、没有拒绝原因
```

后果是具体的：

1. **查不到责任人**：一道题从草稿变成已发布，审计日志里只有"某人编辑了题目"，
   看不出他是**以审核身份**通过的。题目出错时无法回溯"谁审的"。
2. **`rejected` 是空转状态**：被拒的题没有任何"拒绝原因"落点 ——
   出题人只能自己去问，而系统里什么都没留下。
3. **"审核流"没法长出来**：将来要做"待审队列"，第一件事就是补这几个字段；
   而那时 `questions.status` 早被当成普通字段用惯了，历史数据**无从回填**
   （谁在什么时候审的，永久丢失）。

> 换句话说：**这不是"字段还没用上"，是"这段历史从来没被记下来"。**
> 越晚补，可回填的历史越少 —— 但**不必因此急着做**，
> 因为它不影响任何已交付功能（见 §3 为什么可以等）。

## 2. 补齐时的设计原则（先定下来，避免又是"加几个字段"）

### 2.1 一次审核动作 = **四件套**，缺一不可

```
状态 + 人 + 时间 + 理由
```

- **状态**：`reviewing → published` / `→ rejected` —— 现有
- **人**：`reviewed_by` —— 现有字段，未写入
- **时间**：`reviewed_at` —— 现有字段，未写入
- **理由**：**缺字段** —— 拒绝原因 / 审核意见没有落点
  （`exam_attempt_items.review_comment` 有，`questions` / `comments` 没有）

👉 补齐时**不能只接上 `reviewed_by`**，否则还是"审了但不知道为什么"。
`questions` / `comments` 需要一个理由字段（或统一走 `content_change_logs` 的 `diff`）。

### 2.2 审核动作必须是**独立的接口**，不能继续复用"改字段"

现在是 `PUT /admin/questions/{id}` 带一个 `status`。
补审核后应当有明确意图的接口，例如：

```
POST /admin/questions/{id}/review    { decision: "approve" | "reject", comment: "..." }
```

理由（与坑 42 同一条）：

> **一个字段的变化，如果有独立的业务含义，就该有独立的入口。**
> 复用"部分更新"接口，等于让审核和"改个错别字"共用一条路径 ——
> 审计上看不出区别，权限上也没法区分（谁都能改字段，但不是谁都能审）。

顺带：这样做也就自然回答了"审核该归哪个权限" —— 现在的 `question:update`
显然不等于"审核权"。

### 2.3 三处**不要一起做**（比重不同）

| 处 | 为什么可以不一起做 |
|---|---|
| `questions` | 与已交付功能有交集（题库已上线），**优先级最高**，且需要新增理由字段 |
| `comments` | C 端评论区整块未开，**跟评论区一起做**才是自然的 |
| `exam_attempt_items` | 人工批改是 C 端作答链路的一环，**跟作答/批改批一起做** |

## 3. 为什么可以等（不是"以后再说的托词"）

| 理由 | 说明 |
|---|---|
| **不阻塞任何已交付功能** | 题目审核现在靠"改 status"绕过去了，功能是通的 |
| **现在补 = 只有字段、没有消费方** | 没有待审队列、没有审核入口，补了也只是"多几个永远是 NULL 的列" |
| **它是三条不同链路的前置** | 强行挤进状态机批次，会把"状态可达性"和"审核流程"两件事混在一起 —— 正是本批要避免的范围失控 |
| **历史数据本来就在丢** | 早做一天就多记一天；但**边际收益**要放在"审核流程本身要做"的前提下才成立 |

## 8. 第 1 处：`questions`（**本批做**）

### 8.1 写什么（逐字段，含"值从哪来"）

一次审核动作 = **状态 + 人 + 时间 + 理由**（§2.1 的四件套），落到列上：

| 字段 | 写什么 | 从哪来 | approve | reject |
|---|---|---|---|---|
| `questions.status` | 审核结论 | 由接口推导，**不由请求体直接指定** | `published` | `rejected` |
| `questions.reviewed_by` | 审核人 | `actor.id`（登录态） | ✅ | ✅ |
| `questions.reviewed_at` | 审核时刻 | `now()`（**库时间**，不用 Python 时间，避免与 `created_at` 的时钟源不一致） | ✅ | ✅ |
| `questions.published_at` | 首次/最近一次对外发布 | `now()` | ✅ **同时写** | ❌ **不写** |
| `questions.updated_by` / `version` | 与题库已有的写路径保持一致 | `actor.id` / `+1` | ✅ | ✅ |

**理由（拒绝原因 / 审核意见）落在哪 —— 两条路，需裁定**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 复用 `content_change_logs`**（本方案倾向） | 理由进 `diff.after.comment`（不截断）+ `change_log`（截 500） | **不加列、不改 schema**；但"拒绝原因"没有**列级**约束 —— 想列表页直接显示得去 join 日志表 |
| B. 新增 `questions.review_note VARCHAR(500)` | 理由直接落在题目上，列表/详情一 select 就有 | 要一条 **migration** + schema 变更；且与 `content_change_logs` 出现**两处真相** |

> 倾向 A 的理由：`exam_attempt_items.review_comment`（现有设计）与 `comments` 的审核意见
> **本来也是各写各的**，三处字段名不统一；而 `content_change_logs` 是**已经存在**的、
> 已有前端审计抽屉**渲染 `{before, after}` 形状**的通道 —— 理由进它，**零新增存储**。
> ⚠️ 但 A 有一个必须承认的代价：**`change_log` 会被截到 500 字**（现有 `[:500]`），
> 所以完整理由只保证在 `diff` 里（JSONB，不截断）。见 §13 裁定项 ①。

### 8.2 什么时候写（状态机 + 幂等）

**只允许从这三个状态进入审核**（其余拒绝，并给可执行下一步 —— 硬约定 C）：

| 当前 status | `decision=approve` | `decision=reject` | 说明 |
|---|---|---|---|
| `draft` | ✅ → `published` | ✅ → `rejected` | 最常见：直接审草稿 |
| `reviewing` | ✅ → `published` | ✅ → `rejected` | 送审后审 |
| `rejected` | ✅ → `published` | ✅ → `rejected` | 复议 / 再拒（覆盖 `reviewed_at`） |
| `published` | 🟡 **幂等返回** | ❌ `409` | 见下方两条 |
| `archived` | ❌ `409` | ❌ `409` | 要先改回 `draft`（当前只有 `PUT` 能改，见 §13 裁定项 ④） |
| `is_deleted = true` | ❌ `400` | ❌ `400` | 先恢复（与题库其他入口一致） |

**两条硬要求**（都来自已有硬约定，不是新发明）：

1. **幂等判据 = "目标状态是否已达成"**（硬约定 C）：
   `published` + `approve` → 返回当前详情并带 `already=true`，
   **不写 `reviewed_at`、不写 `content_change_logs`、不动 `version`**。
   ⚠️ 尤其不能"因为输入的 decision 是一样的"就当成幂等 —— 那是"输入唯一"，不是"目标已达成"。
2. **`published` + `reject` 必须拒绝**：把一道**已经对外在线**的题直接审成 `rejected`，
   语义上是"悄悄下架"，而不是审核。正解是先归档（`is_deleted`）或走下线动作。
   拒绝时给出下一步文案（`40901`）。

**并发**：请求体带 `version`（与 `PUT /admin/questions/{id}` 同一套乐观锁语义）。
两个审核员同时审同一道题时，后来者拿 `40901`，**不静默覆盖**。

### 8.3 谁来写（接口 / 权限 / actor）

**接口**（新，独立入口 —— §2.2 的理由不变）：

```
POST /admin/questions/{id}/review
body: { "decision": "approve" | "reject", "comment": "...", "version": 3 }
→  200 QuestionDetail   （复用详情结构，前端就地更新，与题库其他写接口一致）
```

**权限：复用 `question:publish`（建议）**，理由：

- **语义完全一致** —— `question:publish` 的定义就是"把草稿推向线上题库"，
  审核通过正是这件事（`import_service` 用它，`admin_imports` 用它，前端已有 `P.questionPublish` 常量）；
- **新增权限码的成本 > 收益，且有个反直觉的事实**：`role_permissions` 是**按 module 整包发放**的
  （`db/schema.sql`：`SELECT 3, id FROM permissions WHERE module IN ('question','exam','stats')`），
  在 `question` 模块里加一条 `question:review`，**会自动发给本来就有 question 模块的角色** ——
  ⇒ **权限分布一点没变**，只是多了"改种子 + 改前端常量 + 改文档"三处同步成本。
- ⇒ 真要表达"审核权责独立"，**得先做角色重组**（让某角色有 `question:update` 但没有审核权），
  那是另一件事。已记为 **BL-08**（`docs/21`）。

**actor（谁）**：`actor.id` 来自登录态 —— **不接受请求体里的"审核人"**。
`reviewed_by` 与 `content_change_logs.operator_id` 必须是**同一个值**（同一事务里同源）。

**拒绝原因必填规则**：`decision=reject` 时 `comment` **必填**（非空白、≤ 500 字）；
`approve` 时可选。理由：§1 里"`rejected` 是空转状态"这条问题的**根因就是没有理由落点** ——
允许"拒绝但不说为什么"等于只补了一半。

### 8.4 留痕落点（两条通道，都要写）

| 通道 | 写什么 | 形状 |
|---|---|---|
| `content_change_logs` | 一条，**`action='review'`**（新枚举值） | `diff = {"before": {"status": "<旧>"}, "after": {"status": "<新>", "decision": "approve\|reject", "comment": "<原文，不截断>"}}`；`change_log = "审核通过：…" / "审核拒绝：…"`（`[:500]`）；`operator_id = actor.id`、`operator_ip = to_inet(ip)`、`batch_id = NULL` |
| `audit_logs` | 一条，`action="question.review"`、`module="question"`、`entity_type="question"`、`before/after` 同上 | 走 `write_audit()`（审计失败不影响主流程） |

> `content_change_logs.action` 是 `VARCHAR(24)`，**无 CHECK 约束** ⇒ 加 `'review'` **不需要 migration**；
> 但 `db/schema.sql` 那一行的注释（`-- create / update / publish / archive / rollback / delete`）
> 要**同步补上 `review`** —— 否则下一个人会以为 `'review'` 是脏数据。

> **为什么用一个新 action 值，而不是复用 `'publish'`**：`reject` 不是 publish；
> 而"能在审计抽屉里按 action 分开筛"正是 §2.2 那条原则（独立业务含义 → 独立标识）的延伸。

⚠️ **顺手发现：`content_change_logs` 现在有 4 个写入点**（2 个 helper + 2 处内联）：

| 位置 | 形态 |
|---|---|
| `question_service._record_change` | helper（`entity_type` 写死 `'question'`） |
| `exam_service._record_change` | helper（`entity_type` 参数化） |
| `user_service`（`update_user_status` 内） | **内联 SQL**（`entity_type='user'`） |
| `import_service`（约 :1706） | **内联 SQL** |

⇒ 第 5 个消费者（审核）落地前，**应当先收口成一个 `content_log_service.record_change()`**，
否则下一次"字段名改了/加个 action"就要改 5 处。**是否本批一起做 → §13 裁定项 ③。**

### 8.5 读回：让"谁审的"能被查出来

写进去不等于查得到（"中间产物生成 ≠ 被消费"）。三处都要动：

## 12. 与现状的冲突（本批必须正面处置，不能"顺手绕过"）

### 12.1 `published_at` 已经有一个洞

`PUT /admin/questions/{id}` 接受 `status`（`QuestionUpdateIn.status: QStatus | None`），
把 status 改成 `published` 时 **`published_at` 不写** —— 只有 `import_service.publish_batch` 写它。
⇒ 库里现在可能已有 **"状态是已发布、`published_at` 为 NULL"** 的题。
审核接口引入后，"发布"这件事就有了**两个入口**，洞会继续扩大。

**处置（需裁定）**：把 `status` 从 `PUT` 的入参里**移除**，发布/驳回只能走 `POST .../review`。
代价是**前端 `QuestionForm` 的 status 下拉框要拆掉**（`QuestionForm.tsx:273`），是行为变化。

### 12.2 `reviewing` 从来没人"系统性地"写过

`reviewing` 只能靠前端下拉框**裸改字段**（同一个 `PUT`），而那个动作
**不记任何审核人、不写任何日志字段**。⇒ 现在库里若有 `reviewing` 的题，
**没有任何记录说明它是谁、什么时候送审的** —— 这正是 §1 说的"历史从来没被记下来"。

**处置**：本批补 `POST /admin/questions/{id}/submit`（`draft → reviewing`）**是否必要？**
—— 见 §13 裁定项 ④。若不补，则 `reviewing` 继续是一个"能写但无意义"的值（硬约定 F 的同族问题）。

### 12.3 本批**不顺手改**的东西（防止范围失控）

- ❌ **不收口** 4 处 `content_change_logs` 写入点（除非裁定项 ③ 同意）

## 15.6 ★★ 新 harness 自己造过一次**假绿**（必须记）

第一版 `mutate-review.py` **漏设 `AI_BASE`**（`conftest.py` 是
`BASE = os.environ.get("AI_BASE", "http://localhost:8000")`）→ 用例全部去连 8000 端口 →
`client` fixture 连不上 → **整个模块 12 条全 skip**。

而 harness 只判了**退出码**，于是：

```
[mutate]   pytest: 12 skipped in 2.39s
[mutate] 基线全绿 ✓                      ← 假的
[mutate]   → ❌ 存活  （M1/M2/M3/M5 各一次）  ← 4 个假"存活"
```

**`pytest` 在"全部 skip"时退出码也是 0。** ⇒ 一次环境配错，产出了 **1 个假绿 + 4 个假红**。

**两层处置**（都要做）：

1. 补 `AI_BASE`（环境配错本身）；
2. **给 harness 加"到底跑了没有"的守卫** —— 基线要求 `passed ≥ 1` **且 `skipped == 0`**，
   并要求摘要行能解析出 passed；否则判 **"未跑成"**（**既不是存活也不是捕获**），并让整轮非 0。
   ⚠️ 关键：**"未跑成"必须与"存活"分开计数** ——
   否则"这一次没跑"会被读成"用例挡不住"，然后人就会去**加强本来没问题的用例**。

> 这与本批的另一条（清场 harness 的"变异只打掉一层"）是同一个家族的第二种形态：
> **判据太松 → 假绿**；**变异没生效 → 假的存活**。两次都是 harness 而不是被测对象的问题。
