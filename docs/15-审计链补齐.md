## 1. 问题：状态**能改**，但"谁改的、什么时候改的"从来没被记录

`docs/14` 审计时按硬约定 F 的判据（"读路径有判断 ≠ 该状态可达"，反向亦然）顺带查了
**审核/批改类配套字段的引用数** —— 结果是 **0**：

| 表 | 字段 | 全仓引用数 | 本该由谁写 |
|---|---|---|---|
| `questions` | `reviewed_by` / `reviewed_at` | **0** | 题目审核动作（`draft → published` 时的审核人） |
| `comments` | `audited_by` / `audited_at` | **0** | 评论审核动作（`pending → approved/rejected`） |
| `exam_attempt_items` | `reviewer_id` / `review_comment` / `reviewed_at` | **0** | 人工批改主观题 |

### 为什么这是个问题（而不是"字段先留着"）

**`questions.status` 的 5 个值全部可达**（创建/编辑接口都接受），
所以从"状态机完整性"看它是正常的 —— 但审核这件事在系统里**只体现为一个枚举值的变化**：

```
现在：  draft ──(PUT /admin/questions/{id} 改 status)──→ published
        没有审核人、没有审核时间、没有审核意见、没有拒绝原因
```

后果是具体的：

1. **查不到责任人**：一道题从草稿变成已发布，审计日志里只有"某人编辑了题目"，
   看不出他是**以审核身份**通过的。题目出错时无法回溯"谁审的"。
2. **`rejected` 是空转状态**：被拒的题没有任何"拒绝原因"落点 ——
   出题人只能自己去问，而系统里什么都没留下。
3. **"审核流"没法长出来**：将来要做"待审队列"，第一件事就是补这几个字段；
   而那时 `questions.status` 早被当成普通字段用惯了，历史数据**无从回填**
   （谁在什么时候审的，永久丢失）。

> 换句话说：**这不是"字段还没用上"，是"这段历史从来没被记下来"。**
> 越晚补，可回填的历史越少 —— 但**不必因此急着做**，
> 因为它不影响任何已交付功能（见 §3 为什么可以等）。

## 2. 补齐时的设计原则（先定下来，避免又是"加几个字段"）

### 2.1 一次审核动作 = **四件套**，缺一不可

```
状态 + 人 + 时间 + 理由
```

- **状态**：`reviewing → published` / `→ rejected` —— 现有
- **人**：`reviewed_by` —— 现有字段，未写入
- **时间**：`reviewed_at` —— 现有字段，未写入
- **理由**：**缺字段** —— 拒绝原因 / 审核意见没有落点
  （`exam_attempt_items.review_comment` 有，`questions` / `comments` 没有）

👉 补齐时**不能只接上 `reviewed_by`**，否则还是"审了但不知道为什么"。
`questions` / `comments` 需要一个理由字段（或统一走 `content_change_logs` 的 `diff`）。

### 2.2 审核动作必须是**独立的接口**，不能继续复用"改字段"

现在是 `PUT /admin/questions/{id}` 带一个 `status`。
补审核后应当有明确意图的接口，例如：

```
POST /admin/questions/{id}/review    { decision: "approve" | "reject", comment: "..." }
```

理由（与坑 42 同一条）：

> **一个字段的变化，如果有独立的业务含义，就该有独立的入口。**
> 复用"部分更新"接口，等于让审核和"改个错别字"共用一条路径 ——
> 审计上看不出区别，权限上也没法区分（谁都能改字段，但不是谁都能审）。

顺带：这样做也就自然回答了"审核该归哪个权限" —— 现在的 `question:update`
显然不等于"审核权"。

### 2.3 三处**不要一起做**（比重不同）

| 处 | 为什么可以不一起做 |
|---|---|
| `questions` | 与已交付功能有交集（题库已上线），**优先级最高**，且需要新增理由字段 |
| `comments` | C 端评论区整块未开，**跟评论区一起做**才是自然的 |
| `exam_attempt_items` | 人工批改是 C 端作答链路的一环，**跟作答/批改批一起做** |

---

## 3. 为什么可以等（不是"以后再说的托词"）

| 理由 | 说明 |
|---|---|
| **不阻塞任何已交付功能** | 题目审核现在靠"改 status"绕过去了，功能是通的 |
| **现在补 = 只有字段、没有消费方** | 没有待审队列、没有审核入口，补了也只是"多几个永远是 NULL 的列" |
| **它是三条不同链路的前置** | 强行挤进状态机批次，会把"状态可达性"和"审核流程"两件事混在一起 —— 正是本批要避免的范围失控 |
| **历史数据本来就在丢** | 早做一天就多记一天；但**边际收益**要放在"审核流程本身要做"的前提下才成立 |

## 4. 触发条件（明确到批次）

| 序号 | 内容 | 触发条件 |
|---|---|---|
| 1 | `questions` 审核四件套 + `POST /admin/questions/{id}/review` | **审核流程立项时**（与 `exams.reviewing`、`comments.pending` 同一批，见 `docs/14` §7.1 / §7.4） |
| 2 | `comments` 审核四件套 | **C 端评论区上线时** |
| 3 | 主观题人工批改（`reviewer_id` / `review_comment` / `reviewed_at`）+ `exam_attempts.scoring` 状态推进 | **C 端作答 / 批改批次** —— 同批必须补 `unpublish` 的"有 N 人在考"校验（`docs/14` §6.4） |

> ⚠️ 第 3 条与 `docs/14` §6.4 是**同一条依赖**：
> `exam_attempts` 一旦开始写入，`unpublish` 就必须先校验进行中的作答。
> 两件事应当在同一批里做，别拆开 —— 拆开就会出现"先上线了下线功能、再补校验"的窗口期。
