## 0. 判据（先把口径定死，否则分类会飘）

### 0.1 "可达"的定义

**只有"当前有任何接口能写入该状态"才算可达。** 具体地：

| 不算可达 | 算可达 |
|---|---|
| 只在 `schema.sql` 的 `DEFAULT` 里 | 任何接口的请求体里有该字段并能传这个值 |
| 只在种子里 `INSERT` 进去 | 服务层有 `status = '<值>'` 的写入 |
| 只在文档 / 注释 / 类型别名（`Literal[...]`）里 | CLI 命令能写（本项目当前没有这类 CLI） |
| 只在**读**路径里被判断（`WHERE status='on'`） | |

> ⚠️ 特别注意最后一条：**"读路径判断了某状态"不等于"该状态可达"**。
> 本审计里最扎眼的缺口就是这一类 ——
> `auth_service` 实现了「`disabled`/`locked`/`deleted` 就拒绝登录」，
> 但**没有任何接口能把账号改成这三个状态**。逻辑写全了，入口不存在。

### 0.2 "是否阻塞"三档

| 档 | 定义 | 判据（一句话） |
|---|---|---|
| **P0** | **影响前端已有功能** | 已知的、**已交付**的模块里，用户按界面上的线索去找一个动作，找不到 / 做了没用 |
| **P1** | **影响未来批次**（审核流程 / 人工批改 / C 端 / 电商 / 运营） | 该状态在**已声明的设计**里有明确用途，但整块业务还没开工 |
| **P2** | **声明了但实际用不上** | 无写入点、无读路径依赖、且**看不出将来谁会用它** → 建议删列/删表或显式标注"预留" |

**P0 的边界我按"宽"处理**：用户明确说 P0 是"用户能点到但接口 404"，
但在实践中还有一类同样难受的表现 —— **界面上摆着一个筛选项，却永远筛不出东西**，
或**设计上承诺了某个能力，界面上却没有入口**。
这两类和 404 是同一件事（功能缺口），只是表现不同。我在 P0 里都标了**具体表现**，
你可以据此改判。

## 2. 字段可达、但**流程**缺失（比"状态不可达"更容易被忽视）

这几张表的状态**能写到**，所以按 §0.1 不算"缺失转换" ——
但支撑这些状态的**字段与动作**一个都没实现。列出来是因为：
**将来做审核流程时，会以为状态机已经就位，结果发现"只能改标志位、不能真正审"。**

| 实体 | 状态 | 相关字段 | 引用数 | 说明 |
|---|---|---|---|---|
| `questions` | `reviewing` / `rejected` | `reviewed_by` / `reviewed_at` | **0** | 没有任何"审核"动作会写这两个字段。当前 `draft→published` 只是改一个枚举值，没有审核人、没有审核时间、没有拒绝原因 |
| `comments` | `approved` / `rejected` | `audited_by` / `audited_at` | **0** | 同上 |
| `exam_attempt_items` | （主观题判分） | `reviewer_id` / `review_comment` / `reviewed_at` | **0** | 人工批改的三个字段全未使用；`exam_attempts.scoring` 状态也就无从到达 |

> 这三个是同一类：**"谁在什么时候做了这个决定"没有被记录**。
> 注意 `questions` 的审核**不阻塞**任何已交付功能（现在靠"改状态"绕过去了），
> 但它意味着**审计链是断的** —— 一道题从 draft 变 published，查不到是谁审的。

## 3. `exams` 的状态机：先把"设计意图"还原出来（P0 的上下文）

`exams` 是全项目**唯一一个既对外承诺了状态、又缺入口**的地方，值得单独说清。

从 `can_*` 三个标志位（都在 `ExamDetail` 里返回给前端）反推设计意图：

```python
can_compose = not deleted and row["status"] in ("draft", "reviewing", "off")
can_publish = not deleted and row["status"] in ("draft", "reviewing")
can_unpublish = not deleted and row["status"] == "published"
```

拼出来的状态机是：

```
                ┌──────────────── reviewing ─────────────┐
                │                                        │
   （创建）→ draft ─────────────────────────────────────→ published
                ↑                                        │
                │                                        ↓
                └──────────── off ←──────────────────────┘
                         （下线：不可对外，但可继续编辑、可重新发布）
```

**已实现**：`→ draft`（创建）、`draft → published`（发布）。
**未实现**：`published → off`（下线）、`off → published`（重新上线）、`draft → reviewing`（送审）、`→ archived`（状态位，见 §4）。

### ⚠️ 决策点 1：`unpublish` 应该回到 **`off`** 还是 **`draft`**？

你给的预期是 `published → draft`。但 **schema 里已经为这个语义准备了 `off`**，
而且 `can_compose` / `can_publish` 都显式把 `off` 算作"可编辑、可发布"。
两者的实际差别：

| 目标状态 | 语义 | 前端文案 | 审计 |
|---|---|---|---|
| `draft` | 回到"还没发布过" | 「转为草稿」 | 丢失"曾经上线过"这个事实 |
| **`off`** | "发布过，现在下线了" | 「下线」 | 保留历史，与 `published_at` 一起读得通 |

**我的建议：用 `off`** —— 它就是为这件事声明的，且不丢信息。
但这会改变你预期里的接口语义，**所以先问**。
（若坚持 `draft`，建议顺带把 `off` 从 CHECK 里删掉，否则 schema 里留着一个永远到不了的状态，就是新的 P2。）

## 4. P2 清单：建议"删列/删表"还是"标注预留"

| 项 | 现状 | 我的建议 | 代价 |
|---|---|---|---|
| `import_batches.parsing` | CHECK 里有，6 个写入点里没有它 | **删掉** `parsing` | 一条迁移改 CHECK 约束；需确认没有历史数据是 `parsing` |
| `exams.archived` | 与 `is_deleted`（归档位）**语义重复**，且从未写入 | **删掉** `archived`，或明确"`archived` 表示已停用（业务下线且不再复用）"并给出入口 | 需确认与 `off` 的区别能说清，否则两个都留着只会让人选错 |
| `dictionaries.status` | **无 CHECK 约束**（唯一一张） | **补上 CHECK**（`on`/`off`） | 一条迁移；需先扫一遍存量值 |
| `sms_logs` | 整张表 0 写入（连读也没有） | 标注"**预留：真实短信通道**"，暂不删表 | 无 |
| `dictionaries` 表整体 | 无接口、无读路径 | 标注"预留"或与 `app_configs` 合并评估 | — |

> **P2 的处置原则建议**：**只是"现在不用"的标"预留"，"和别的东西重复"的才删。**
> 删表/删列要走迁移，成本不低；而"预留"只要一行注释。
> 但 `exams.archived` 这种**语义重复**的必须处理 —— 留着它，下一个人会以为
> "归档有两种"，然后在两条路上各写一半逻辑。

## 5. 附表：`is_deleted` 的覆盖面（与本次审计相邻的坑）

`is_deleted` 是另一套"生命周期"，和 `status` **正交**（项目里已经明确过：
软删除 ≠ 业务归档）。这里只列**哪些表有、哪些没有**，
因为"以为所有表都有 `is_deleted`"是已经踩过的坑（`subjects` 上撞过 `UndefinedColumnError`）。

| 有 `is_deleted` | 没有 `is_deleted` |
|---|---|
| `users`、`products`、`orders`、`chapters`、`knowledge_points`、`courses`、`lessons`、`notes`、`comments`、`questions`、`exams`、`announcements` | `subjects`（用 `status on/off`）、`paper_rules`（用 `status`）、`exam_sections`、`exam_questions`、`question_versions`、`content_change_logs`、`import_batches`、`import_items` |

**规律**：**内容型实体**（题/卷/章节/课程/评论）有软删除；
**配置型 / 关联型实体**（科目、规则、分段、卷面行、批次）没有 ——
它们的"消失"要么靠状态位，要么靠**物理删除**（`paper_rules` 就是硬删除，§3.7 已记录）。

> 这条规律值得写进 schema 顶部注释：**新增表时先想"它属于哪一类"**，
> 想好了 `is_deleted` 要不要加、状态列要不要加，就不会出现
> "有的表两套都有、有的表一套都没有"的随机分布。

## 8. 审计方法（可复用，便于复核）

本表不是靠读文档推出来的，全部是从**代码里实际存在的写入点**反推的。做法：

1. **取声明**：从 `db/schema.sql` 抽所有 `status` 列 + 其 `CHECK (status IN (...))`。
   ⚠️ **不要查 `db/models.py`** —— 它只映射 8 张表，不代表库里没有。
2. **取可达**：全仓 grep 三类写入 —— `UPDATE <表> SET status`、`INSERT INTO <表>` 里的 status 值、
   服务层的 `"status": "<值>"`；再逐个确认它确实是写库（而不是构造响应）。
3. **反向验证**：对每个"疑似不可达"的状态，再 grep 一次**该状态字面量** ——
   若只出现在 `Literal[...]` / 注释 / docstring 里，就确认不可达。
4. **顺带查读路径**：`WHERE status = 'x'` 说明该状态**有语义**（不是死枚举），
   于是"不可达 + 有读路径"就是真缺口（`users.disabled` 就是这么抓出来的）；
   "不可达 + 无读路径"则是 P2。
5. **顺带查配套字段**：审核/批改类字段（`reviewed_by` / `auditor_id` / `review_comment` …）
   引用数为 0 → 状态可达但**流程缺失**（§2）。

> 建议把 1–2 步固化成一个脚本（`tools/local-verify/audit-state-machine.py`），
> 第二批加实体时能**重跑对比**，而不是重新人肉过一遍。
> 本段**没写**这个脚本（只出表），需要的话第二段一起做。
