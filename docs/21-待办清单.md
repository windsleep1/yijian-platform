## 1. 规则：一条"待办"必须满足三个条件（2026-09-25 定，硬约定 P）

| # | 条件 | 反例（不达标） |
|---|---|---|
| 1 | **有编号** —— 每条在文档里有唯一 ID | "记得优化一下" |
| 2 | **有触发条件** —— "**X 发生时做**"，不是"重要时做" | "以后有空再说"、"后续优化" |
| 3 | **有检查点** —— 每批收尾扫一遍清单，看有没有触发 | 写了但没人再看 → 退化成"一个数字" |

> **不满足三条件的"待办"，要么现在做，要么明确写"不做 + 理由"。**
> **"以后想起来"不构成待办 —— 它是逃避。**

**为什么必须有检查点**：前两条只保证"写得清楚"，**没有任何交付流程会因为"当时说过"而停下来**
（同 `.coveragerc` 里"抬升规则"那条：门槛一旦写死就没人回头看，棘轮退化成数字）。
所以第 3 条的落点是**机械动作**：`apps/admin/docs/B端联调坑.md` 附录「一批交付收尾的固定动作」**§8**。

**触发条件的判据本身也要验**（硬约定 J）：一条触发条件若**当天就已满足**，它不是"以后要做"，
而是"现在做"或"假条件" —— 本项目已抓到一次（**BL-04**，用户原话"角色数 ≥ 3"，而种子里已有 7 个角色）。
⇒ 写触发条件时**必须回头查一次"它现在是不是已经成立"**。

### 4.3 BL-10 的来历：门禁"**能覆盖**"与"**能过**"是两件事（2026-09-25 实测）

用户给的判断标准：**存量 ≤ 20 条 → 顺手清掉并纳入门禁；> 20 条 → 记待办、独立成批**。

### 4.4 BL-14 的实测：你给的索引表达式**有两处不成立**（2026-09-26）

原话：*"加唯一约束：`(user_id, date(created_at)) WHERE mode='daily' AND is_deleted=false`"*。

在真 PG 16 上用 **TEMP 表**实测（不碰任何真实表），逐条：

| # | 表达式里的部分 | 实测结果 |
|---|---|---|
| 1 | `date(created_at)` | ❌ **建不出来**：`ERROR: functions in index expression must be marked IMMUTABLE`。<br>`date(timestamptz)` 的结果依赖会话 `TimeZone`（是 **STABLE** 不是 IMMUTABLE），PG 拒绝把它放进索引表达式 |
| 2 | `AND is_deleted = false` | ❌ **列不存在**：`ERROR: column "is_deleted" does not exist`。<br>`practice_sessions` **没有** `is_deleted`（有的是 `chapters` / `questions` / `knowledge_points` 那类） |
| 3 | 修正后的表达式 | ✅ **可建，且真的拦重复**：同用户同一天两条 `daily` → `duplicate key`；**不同 mode 不冲突**（`chapter` 照常插入） |

**修正版（已实测）**：

```sql
CREATE UNIQUE INDEX uq_practice_daily
  ON practice_sessions (user_id, ((created_at AT TIME ZONE 'Asia/Shanghai')::date))
  WHERE mode = 'daily';
```

- 用 `AT TIME ZONE 'Asia/Shanghai'` 而不是裸 `date()`：**既解决 IMMUTABLE，又与 Batch 8 定的
  "日界 = Asia/Shanghai"口径一致**（两处口径不能各说各话 —— 这正是 `docs/20` §14 那条口径红线的延伸）；
- 去掉 `is_deleted`（列不存在）。

**⚠️ 迁移风险（实测，这条最容易被漏）**：若上线时库里**已有**重复（这条约束从未存在过，所以很可能有），
建索引会**直接失败**：

```
ERROR: could not create unique index "uq_t3"
DETAIL: Key (user_id, …)=(300, 2026-09-26) is duplicated.
```

⇒ 加索引**之前**必须先跑一次"有没有重复"的检查，并按产品口径决定**合并策略**（保留哪一条、合并作答记录否）。
**这也是它必须在"做 daily 那个批次"里做、而不是当成一句 DDL 顺手加的原因。**

**迁移三步（用户 2026-09-26 要求写成"执行步骤"，不是"提醒"）**：

| 步 | 动作 | 判据 / 产物 |
|---|---|---|
| **1** | **先查重复**：把下面的查询跑一遍（**结果为空才能进第 2 步**） | `SELECT user_id, (created_at AT TIME ZONE 'Asia/Shanghai')::date AS d, count(*)<br>FROM practice_sessions WHERE mode='daily' GROUP BY 1,2 HAVING count(*) > 1;` |
| **2** | **定合并策略**：保留最新 / 保留最早 / 合并作答记录 —— **当场选一个并写进迁移文件注释** | 选不出来 = 需求没定，**别往下走**（同 BL-11 的"三选一，不许再看"） |
| **3** | **再建索引**（全部落在 `db/migrations/*.sql`，不在 schema.sql 里"顺手改"） | `CREATE UNIQUE INDEX uq_practice_daily ON practice_sessions (user_id, ((created_at AT TIME ZONE 'Asia/Shanghai')::date)) WHERE mode = 'daily';` |

⚠️ 第 1 步的查询**必须用 `AT TIME ZONE 'Asia/Shanghai'`**：迁移脚本里用裸 `date(created_at)`
会**在 CI 的不同会话时区下算出不同的"天"**，那样"查重复"和"建索引"会用两套日界 ⇒ 建索引时仍然撞重复。

### 4.5 BL-16 的执行方案：把"沉默的 12 分钟"变成"会说话的失败"

**为什么现在下不了手**：匿名调用是**拿不到 job 日志的**（403）——
`actions/runs/{id}/jobs` 只给**每一步的名称/状态/起止时间**（元数据够用），**不给日志内容**。
所以现在能确定的只有：

```
pytest 步骤：02:40:06 → 02:52:18 = 12 分 12 秒（= timeout-minutes: 12 被撞）
后续步骤「覆盖率门禁」：skipped  ← 覆盖率门槛这些天**一次都没生效**
```

**两条出路（推荐 ①，因为 ② 依赖别人）**：

| # | 做法 | 代价 / 风险 |
|---|---|---|
| **① 让挂起的用例自己说话** | 装 **`pytest-timeout`**，CI 里加 `--timeout=60`（或 `-p timeout --timeout=60`）<br>⇒ 挂住的用例**按名字失败**，并把首尾堆栈打进日志 | 需要一次 CI 迭代；但**不修根因、只让失败有界且可读** —— 与 `timeout-minutes` 当初的定位完全一致 |
| **② 要一份日志尾部** | 让用户从 Actions 页面复制 pytest 那一步的输出尾部（匿名读不到；API 403） | 成本最低，但**依赖人工**；且日志可能**没有任何有用输出**（被 kill 时往往只有开头几行） |

**为什么倾向 ①**：`timeout-minutes` 只证明"**整步**超时"，而**挂在哪一条用例上仍未知**；
`pytest-timeout` 把粒度从"整步"降到"单条用例"，**同时**给出用例名与堆栈 ——
这正是坑 57 的教训（"不说话的失败等于没有失败"）在**测试粒度**上的同一条推论。

⚠️ **别先动 `timeout-minutes`**：它是最后一道闸（硬约定 N）。**在证明"测试里不存在无界等待"
之前移除它**，等于把"有界的失败"换回"无限期挂住"。

| 第二次 CLI 覆盖第一次 | 查 `--append` | ❌ **CI 也用了** `--append` |
| 覆盖率采集方式不同 | 比三份数据文件名 | ❌ 都是 `.coverage.api/.cli/.tests` |

**剩下的候选**（本地**无法判定**，必须靠 CI 报逐文件）：
① **数据依赖分支**：本地 PG（`…pg/data16`）是**跨会话累积**的，CI 的 Postgres 是**每次全新容器**
   ⇒ "有没有既存配置行"这类分支可能不同（`config_service.py` 本地仅 57%，最像）；
② 时序相关分支（雪花 ID 的等待、重试循环）；
③ 库在 Windows / Linux 上的行为差异（异常类型 → 走哪个 `except`）。

⇒ **本批把 CI 的报告粒度提到"逐文件"**（`::notice title=覆盖率逐文件::`，行间 `%0A`，
因为**每个步骤的 notice 有数量上限**，整表塞一条），**同时把 pytest 的 `N passed, M skipped`
也推出去**（"CI 与本地跑的是不是同一批用例"必须能验证）。
**下一次 push 就能逐文件 diff，把那 2 行钉死。**

> ★ 这一步本身就是用户 2026-09-27 定的判据的兑现：
> **任何门禁的关键数字，必须走匿名可读通道** —— 而"能读到 TOTAL"**还不够**：
> `TOTAL` 只说"差几行"，**不说"差在哪"**。报告粒度要跟得上要回答的问题。

### 4.12 ✅ BL-07 闭合（2026-09-27 第二轮）：**差在 1 个文件的 2 行 —— 而且是"本地被历史数据抬高"，不是 CI 漏测**

run `36281095624`（`218301c`，`success` 2m10s）—— **逐文件出口生效**，一读就分出了三类候选：

```
::notice title=覆盖率逐文件  → 17 行；与本地 16 行**逐格相同**，唯一多出的一行：
    apps/api/app/services/import_service.py    611    2    99%     ← ★ 本地该文件是 100%
::notice title=pytest 摘要   → 320 passed, 1 skipped in 68.12s
本地同一次                → 320 passed, 1 skipped in 150.66s
```

★★ **pytest 计数完全一致** ⇒ **不是"用例选择"问题**（既不多跑也不少跳）⇒ 同一批用例里
**某个分支走了不同路径** ⇒ 直接指向"**数据/状态依赖**"（你判断的 🔴），只是文件是
`import_service.py` 而不是 `config_service.py`。

**定位过程（每一步都是"看到"，不是"推理"）**：

1. 该文件里唯一的 2 行异常块 = **`1427-1428`**：
   ```python
   def _stored_file_size(batch_id, file_type) -> int | None:
       try:    return _batch_file_path(batch_id, file_type).stat().st_size
       except OSError: return None        # ← 1427-1428
   ```
   它只在**列表视图**被调用（`:763`），**无用例显式覆盖**、**产品里也没有清理逻辑**。
2. 原始文件落在 **`Path(tempfile.gettempdir()) / "yijian-import-files"`**（`:1400`）——
   **系统临时目录**；而**本地 DB（`…pg/data16`）跨会话累积**（本地管道**不重建库**）。
3. 直接查库核对（`SELECT id, file_type FROM import_batches` + 逐个查文件是否存在）：

   ```
   batch rows        = 1541        raw files on disk = 1796
   rows with NO file = 53          ← 关键数字
   newest 10 / 50 / 100 / 200 行里，无文件的行 = 1 / 1 / 2 / 5
   ```
4. 列表查询是 `ORDER BY created_at DESC, id DESC LIMIT/OFFSET`，测试确实用 `page_size=100`
   ⇒ **本次运行的列表调用必然撞上"无文件"的行** ⇒ `except` 被走到。

⇒ **结论**：本地 `Miss=214` 是**被历史数据抬高的**；**CI 的 `216` 才是干净基线**（全新库 ⇒
每条被列出的批次都还有文件 ⇒ 那个 `except` 永远走不到）。**没有任何产品缺陷。**

**处置**：
- **BL-07 闭合**（对账完成，且差异**完全解释**，**不需要"容忍阈值"**——
  能钉死的差异就不该用阈值糊过去）。
- 新增 **BL-17**：**本地全量管道加"全新库"模式**（或明确记为"本地数字仅供参考"），
  否则每次本地/CI 对比都会重复踩这一条。触发条件：下一次要用本地覆盖率数字做判断时。
- 这条也把 §4.11 那句"**先证明可比**"落到了实处：当时列的四项里，**"数据新旧"就是答案**。

### 4.13 ✅ BL-17 闭合（2026-09-27 第三轮）：本地管道默认跑「一次性库」—— **顺带揪出 3 个被掩盖的缺陷**

**目标**（用户 2026-09-27 定）：本地跑测试的**数据状态**要与 CI 可比。
方案**不是**"加一个 `-Fresh` 开关"（**开关会忘**），而是**把默认行为改成"与 CI 可比"**：

- 默认跑 `yijian_smoke_<pid>`（一次性，跑完销毁）；**开发主库 `yijian` 继续累积**（那是它的用途）；
- 要跑在累积库上（故意为之的调试）：显式 `-DbName yijian` / `--db yijian`。

**改动**：

| 文件 | 说明 |
|---|---|
| `tools/local-verify/smoke-db.py`（新） | 一次性库的建/销毁：`name` / `ping` / `provision` / `drop` / `url` |
| `tools/local-verify/run-local-pipeline.py`（新） | 本机唯一能跑全量的管道（`subprocess.Popen` 版），**收编自 `%TEMP%/yb-pipe.py`** |
| `tools/local-verify/run-smoke.ps1` | 默认 `-DbName ""` ⇒ 一次性库；建库/建表/迁移**委托** `smoke-db.py` |
| `tools/local-verify/serve_fake_redis.py` | 🔴 **强制覆盖 `DATABASE_URL` ⇒ 改 `setdefault`**（见下，这是真因） |

★ **唯一安全闸** `smoke-db.py::assert_smoke_db()`：只接受 `yijian_smoke_<...>`。
**拿它去删开发主库 `yijian` 会被拒**（真 PG 上实测 rc=1）。它不是"注释里提醒一句"，
而是**可执行 + 可证伪**：`--self-test` 20 项里 7 项是"各类非法名字必须被拒"，
**打掉闸门即变红**（变异验证已做）。

★ **为什么把 `%TEMP%/yb-pipe.py` 收进仓库**：它是"本机唯一能跑全量的路径"，
却住在**会被清空的临时目录**里、也进不了版本控制 —— **一个唯一的验证路径不该住在那儿**。

#### 验证结果（本机）

```
320 passed, 1 skipped in 161.63s        ← CI: 320 passed, 1 skipped      ✅ 一致
TOTAL                             4672    216    95%
逐文件 import_service.py           611      2    99%   ← CI 同格也是 611/2/99%
```

**逐文件也对上了** —— 而 `import_service.py` 正是 §4.12 里"**本地 100% / CI 99%**"的那个文件。
⇒ **§4.12 的结论得到独立复现**：本地那 2 行确实是**被历史数据抬高**的，
干净库上就回到 CI 的数字。（这也说明 BL-07 与 BL-17 是同一件事的两头。）

#### ★★ 真正值钱的部分：换默认环境 ⇒ 一次揪出 3 个"被掩盖"的缺陷

**"让默认环境变干净"不只是为了数字可比 —— 它本身就是个 bug 探测器。**
把默认从"累积库"换成"全新库"后，**第一次跑就炸**，连锁揪出三个：

| # | 缺陷 | 为什么以前看不见 |
|---|---|---|
| 1 | **`serve_fake_redis.py` 强制 `os.environ["DATABASE_URL"] = "…/yijian"`**（库名写死） | CI 的库名**恰好就是** `yijian` ⇒ 覆盖后毫无变化 ⇒ **永远不报错** |
| 2 | **本地管道漏了「题库种子」步骤** | 它跑的**累积库**里题库早就有了 ⇒ 这一步**从来不需要** ⇒ 漏了也没人发现 |
| 3 | **`run-smoke.ps1 -DbName <库>` 对 API 进程无效** | 与 #1 同源：API 被写死到 `yijian`，而默认值恰好是 `yijian` ⇒ 参数"看起来能用" |

**#1 的现场**（29 条用例失败的真因）：

```python
os.environ["DATABASE_URL"] = f"postgresql+asyncpg://yijian@127.0.0.1:{args.pg_port}/yijian"
```

API 被静默指向**累积库**，测试却直连 `DATABASE_URL` 指的**一次性库** ⇒
**"写进 A、去 B 里查"** ⇒ 29 条全红，形态都是 `assert ex["code"] == 0` 通过、
紧接着 `assert len(got) == 2` 拿到 `[]`。

**定位它靠"看到"而不是"推理"**（硬约定 P）：`--keep-db` 把库留下来，**直接查表**：

```
questions=6000   content_change_logs=0   import_batches=0   users=1
```

`users=1` 只有 `seed-admin` 建的超管 —— **而测试明明成功创建了几十个用户**。
**"CLI 进程写的在、API 进程写的不在"** ⇒ 一句话锁定"API 连的不是这个库"。

**#2 的同一条推理**：`31 failed → 29 failed` 那次，失败用例名（组卷 / 知识点下拉 /
批量删除）与 `run-smoke.ps1` 注释里「**坑 51**」点名的**一模一样**（"在真正全新的库上
会有 32 条用例失败"），补上 `seed-questions.py` 步骤即可。
★ 注意它**没有一次修完**（只修好 2 条）—— 剩下 29 条是 #1。
**两个缺陷叠在一起，"只修一个"看不到全绿**：这正是"多处缺陷叠加"的又一实例（坑 65）。

#### 判据（两条，本次新增）

- ★★ **"在 CI 上恰好成立"的硬编码**：任何**写死**的库名 / 端口 / 路径 / 主机，
  只要 CI 的环境恰好与之相符，就**永远不会报错**。判据：**同一份代码，换一个"非默认"的
  库名再跑一遍，还成立吗？**（本次：`DATABASE_URL` 被写死成 `.../yijian`。）
- ★★ **"在脏环境上恰好不需要的步骤" = 隐藏的缺失步骤**：一个步骤如果**只在干净环境下**
  才需要，而日常都跑在脏环境上，那它**缺失也不会被发现**。判据：**把环境清空跑一遍，
  缺的步骤自己会浮出来。**

#### 附：两个工具侧的小坑（同批解决）

- **`argparse` 的"参数位置"有两种错法，一种报错、一种静默**（2026-09-27 实测）：
  ① 主解析器的可选参数**写在子命令之后** → 报 `unrecognized arguments`；
  ② 主解析器与子解析器**两边都定义**同名参数 → **子解析器的默认值会静默覆盖主解析器
  解析到的值**（`--port` 默认值恰好相同 ⇒ **完全看不出来**，最危险的那种）。
  ⇒ 公共参数**只挂子命令**，调用方统一写成 `子命令 --psql … --port …`；
  并把这条**落成 `--self-test` 的断言**（变异"把公共参数挂回主解析器" ⇒ 必红）。
- **验收口径**：`smoke-db.py --self-test` 20/20；变异两次均变红（打掉安全闸 → 7 项红；
  挂回主解析器 → 1 项红）；`ruff check .` 全仓 0 条。
