> **为什么要单独一份**：这不是"改个过滤条件"，而是把一条**分散在多个入口的准入判据**
> 收成一处。做完之后"数据范围"才从**列表页的属性**变成**整个题目模块的属性**。

## 1. 现状：一份判据，八个入口，只有一个在用

`question_service.scope_subject_ids()` 一直是数据范围的**唯一事实源**，文档里也这么写着。
但收口前真正**调用**它的只有三处：

| 调用方 | 用途 |
|---|---|
| `question_service.apply_data_scope` | 题库**列表**筛选 |
| `exam_service._scope_clause` | 试卷 / 规则**列表**筛选 |
| `import_service` | 导入的**批次科目 + 逐行**校验 |

也就是说：**范围只作用在"列表"这一类查询上**。

而题目模块还有七条入口，它们**都收到了** `actor: ScopeViewer`，**却一次都没读过它** ——
形参躺在签名里，等于没有：

| # | 入口 | 收口前 | 收口后 |
|---|---|---|---|
| 1 | `GET /admin/questions` | ✅ 有（`apply_data_scope`） | ✅ |
| 2 | `GET /admin/questions/{id}` | ❌ **任何人可按 id 直读** | ✅ `40301` |
| 3 | `POST /admin/questions` | ❌ **可往任意科目建题** | ✅ `40301` |
| 4 | `PUT /admin/questions/{id}` | ❌ **可改任意科目的题** | ✅ `40301`（含"搬科目"） |
| 5 | `DELETE /admin/questions/{id}` | ❌ **可删任意科目的题** | ✅ `40301` |
| 6 | `POST /admin/questions/batch-delete` | ❌ 同上，且**批量更隐蔽** | ✅ 整批 `40301` |
| 7 | `POST /admin/questions/{id}/restore` | ❌ 可恢复别科目的题 | ✅ `40301`（含幂等分支） |
| 8 | `GET /admin/chapters/tree`、`/knowledge-points` | ❌ 下拉**列出全部科目** | ✅ 只列有权限的 |

> ⚠️ 这张表最值得记住的不是"缺了七条"，而是**列表过滤会制造"范围已经生效"的错觉**：
> 验收时打开题库列表一看是干净的，就以为收口做完了。
> **列表过滤防的是"翻到"，防不了"猜到"** —— 知道 id 就能直达。

## 2. 口径（先定判据，再动手）

### 2.1 判据：凡是按 id 寻址的入口，都必须自己再拦一次

问的不是"有没有做过滤"，而是"**能不能不经过列表直接到达这个对象**"。
两者是**不同的攻击面**，前者做了不等于后者做了。

### 2.2 报 `40301` 而不是 `40401`

对象**确实存在**，只是不归你。报 404 会让排查的人以为 id 写错了，
去找一个并不存在的问题 —— 反而绕远路。

> 与硬约定 A 划清界限：那条说的是"只读函数**夹带**比调用方更严的准入"（坑 38）。
> 本条是**准入判据本身**，读路径与写路径**共用同一份**实现，不存在上下层不一致。

### 2.3 授权判断必须排在"业务状态披露"之前

`restore` 的幂等分支（"本来就没删" → `200` + `already_active=true`）如果排在范围闸之前，
越权者能靠它拿到 **200** —— **等于用返回值确认了对象存在**。
所以顺序固定为：**取对象 → 404 → 范围 40301 → 状态判断 → 业务规则**。

### 2.4 批量入口不能把"越权"降级成 `skipped`

`batch-delete` 的既有语义是「已删除 / 不存在的进 `skipped`，不报错」。
但 `skipped` 的语义是"**目标状态已达成 / 对象不存在**"—— 那些情况下继续处理其余几条是合理的。
**越权不属于这一类。**

若为了"友好"把越权也塞进 `skipped`，会同时踩两个坑：

1. **批量入口变成比单条入口更弱的闸**：单条删 `40301`，批量删只给一句 `skipped`。
   越权者改走批量接口就绕过去了 —— **静默忽略在攻击面上等于放行**。
2. **越权尝试被当正常操作写进审计日志**：`after.ids` 里只有真正删掉的那些，
   审计员按 `action='question.batch_delete'` 查，看到的是一次**成功的批量删除**。

判据（就是硬约定 C 那条）：**要不要"放过"，看目标状态是否已达成。**
越权不是"已达成"，是"不许" → **整批拒绝、零副作用、说清是哪几条**。

### 2.5 编辑要拦**两个**科目

`subject_id` 是可改字段。只拦"当前所属"，就能把自己科目的题**搬进**一个没被授权的科目
—— 等于绕过新建时那道闸。所以：当前所属 + 目标科目，两个都拦。

## 3. 改动清单

### 3.1 判据收到一处（`question_service.py`）

```python
def ensure_subject_visible(viewer, subject_id, what="该科目") -> None:
    """科目的准入闸：不在数据范围内就 40301。与 scope_subject_ids 同一份判定。"""
    allowed = scope_subject_ids(viewer)
    if allowed is None:            # global：不限制
        return
    if subject_id not in allowed:  # 空集（未映射的 professional/course）→ 全拒
        raise forbidden(f"{what}不在你的数据范围内（当前账号只被授权了 {len(allowed)} 个科目）", 40301)


def scope_clause(viewer, column) -> tuple[str, dict]:
    """给**原生 SQL** 用的范围片段。空集也必须真的生成 SQL —— = ANY(空数组) 恒假才是失败关闭。"""
```

`apply_data_scope`（`QuestionQuery` 形态）与 `scope_clause`（原生 SQL 形态）都调
`scope_subject_ids`，**同一判定的两种形态**，口径不会漂。

### 3.2 消掉 `exam_service` 的第二份副本

`exam_service` 原先自己实现了一份 `_visible_subject_ids` / `_ensure_subject_visible` /
`_scope_clause`（19 个调用点）。收口时把它删掉、改成**别名**：

```python
_visible_subject_ids = scope_subject_ids
_ensure_subject_visible = ensure_subject_visible
_scope_clause = scope_clause
```

保留旧名是为了 19 个调用点不用动；**实现只剩一份**。
否则"唯一来源"只是写在文档里的一句话，两份副本迟早漂。

### 3.3 八条入口各加一处调用

| 入口 | 位置 | 说明 |
|---|---|---|
| 详情 | `get_question_detail` | 取行后立刻拦 |
| 新建 | `create_question` | **在 `_ensure_subject` 之前**（任何写库动作之前） |
| 编辑 | `update_question` | 当前所属 + `payload.subject_id` 两个 |
| 删除 | `soft_delete_question` | 取行后拦 |
| 批量删除 | `batch_soft_delete` | 整批判定，越权 → `40301` 且零副作用 |
| 恢复 | `restore_question` | **排在幂等分支之前** |
| 章节树 | `list_chapter_tree` | 显式传科目 → 拦；不传 → 用 `scope_clause` 收口科目清单 |
| 知识点 | `list_knowledge_points` | 同上（`kp.subject_id`） |

## 4. 证据

### 4.1 用例（8 条，`tests/test_admin_v4.py`）

用 `researcher` 而不是 `viewer`：种子里 researcher 拿满了 `question` 模块的
read/create/update/delete，**八条入口它全部打得通**，正是"越权"要测的那个面
（viewer 连 `question:read` 都没有，测不出范围这件事）。

- `test_scope_detail_wall` — 按 id 直读别科目 → `40301`
- `test_scope_create_wall` — 越权新建 → `40301` **且库里一道都没多**
- `test_scope_update_wall_including_moving_subject` — 改别科目 → `40301`；**搬科目** → `40301`；改动未落库
- `test_scope_delete_and_restore_wall` — 删 / 恢复（**含幂等分支**）都拦
- `test_scope_batch_delete_is_all_or_nothing` — 混入一条越权 → 整批 `40301`，**两道题都没被删**
- `test_scope_dropdowns_are_filtered` — 下拉只列有权限的科目；显式要范围外 → `40301`
- `test_scope_fails_closed_for_unmapped_scope_type` — 只挂 `professional` → 可见集合为**空集**，全拦
- `test_scope_global_role_unrestricted` — **对照组**：`global` 不受限制（收口不能把全局岗一起收掉）

### 4.2 ★ 变异验证：证明用例真的在守门

"用例通过"不等于"用例在守门"。把唯一的判定点打掉再看：

## 5. 遗留（明确不在本次范围）

1. **`admin_audit` 的可见面**：审计日志目前**不按科目收口**（审计岗是全局岗，`viewer` 就是这样）。
   什么时候要收，取决于"是否会出现只该看某个科目的审计员"—— 现在没有这种岗位。
2. **课程 / 专业范围仍未映射**：`scope_type` 的 `professional` / `course` 一律**失败关闭**
   （收敛到空集）。这是刻意的，见 `scope_subject_ids` 的说明；等真正需要跨科目专业分组时再做映射，
   届时 `ensure_subject_visible` 不用改（它只消费集合）。
3. **`exam_service` 的别名是过渡态**：19 个调用点仍用 `_xxx` 旧名。将来重命名时
   把调用点一并改成 `question_service.ensure_subject_visible`，别名即可删掉。
4. **前端无改动**：下拉返回的就是"能选的"，前端渲染拿到的东西本来就对。
   若将来前端要"置灰而不是隐藏"范围外选项，那时才需要把范围也下发给前端。
