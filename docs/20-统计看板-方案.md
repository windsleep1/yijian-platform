## 0. 一句话

在现有管理后台里加一个 **`/dashboard`** 页面：4 个区块（指标卡 / 趋势 / 分布 / 漏斗），
数据来自**已有表**（不新建业务表），后端 5 个聚合端点 + Redis 缓存，前端 1 个图表库。

**本批真正要解决的问题**（不是"把数字画出来"）：

| # | 工程问题 | 为什么它对个人项目也真实 |
|---|---|---|
| 1 | **聚合查询**：`GROUP BY` / 窗口函数 / **时间序列补空日** | 折线图缺天是最常见也最难自查的错（数据对了、图是错的） |
| 2 | **缓存策略**：读多写少的边界画在哪 | 画错的两端都是坑 —— 缓存太短=没缓，太长=看板说谎 |
| 3 | **多维筛选**：时间范围 / 科目 / 专业 组合起来的状态管理 | 组合爆炸下"可刷新、可分享、可回退"必须落在 URL 上 |
| 4 | **零分母与时区** | 两者都是**不会报错**的错（0.00% 与"今天少了 8 小时"） |

## 1. 先说清"数据从哪来"

### 1.1 现成原料（`db/schema.sql` 里**已经有**，本批不新建表）

| 表 | 本批用途 |
|---|---|
| `users` | 新增用户、DAU 分母、`register_source` 分群 |
| `user_profiles` | **专业**（`major` / `professional`）、`exam_level`、地区 —— 用户维度分群 |
| `practice_sessions` / `practice_items` | **答题量 / 正确率 / 时长**（`items` 是权威明细，`sessions` 是汇总） |
| `exam_attempts` / `exam_attempt_items` | 模考：得分、`is_pass`、`rank_no`、`score_percentile` |
| `user_question_state` | 掌握度、已练题数、错题数（**用户×题**的状态机） |
| `wrong_questions` / `user_wrong_reasons` | 错题 Top、错因分布（`reason_tag`） |
| `questions` | 分布维度：`subject_id` / `type`(7 种) / `difficulty`(1–5) / `exam_year` / `source_type` |
| `subjects` | 科目与**专业课所属专业**（`category` ∈ public/professional、`professional`） |
| `question_stats` | 题维度正确率与**区分度**（`discrimination`） |
| `orders` / `payments` / `entitlements` | 漏斗第三段（`orders.status='paid'` + `amount_cents`） |

### 1.2 ⚠️ 两类"看起来有、其实是空的"（**这条决定 §3.4**）

- **预聚合表**（`daily_study_stats` / `user_subject_stats` / `user_knowledge_stats` / `question_stats`）
  —— schema 里建好了、字段也正好是看板想要的，**但没有任何写入方**：它们是 C 端答题链路要维护的，
  而 C 端还没落地。
- **原始表**（`practice_items` / `exam_attempts` …）同样**一行数据都没有**。

⇒ 两个直接后果：

1. **本批必须自带造数脚本**（§6），否则整个看板是 0 —— 而"全是 0 的看板"看起来还挺正常。
2. **v0.1 只读原始表，不读预聚合表**（理由与切换判据见 §3.4）。

## 2. 指标定义（每个指标算的是什么）

> 原则：**每个指标都要能写出分子/分母**。写不出来的一律不做 —— 那是"数字"，不是"指标"。

### 2.1 指标卡（`overview`）

| 指标 | 口径 | 数据源 |
|---|---|---|
| **DAU** | 当日**有学习行为**的去重用户数（答题 ∪ 交卷 ∪ 有学习时长） | `practice_items.answered_at` ∪ `exam_attempts.submitted_at` ∪ `daily_study_stats.study_minutes>0` |
| **新增用户** | 当日 `created_at` 的用户数（排除 `is_deleted`） | `users` |
| **答题量** | 当日 `answered_at IS NOT NULL` 的条数 | `practice_items` |
| **正确率** | 当日 `count(is_correct=true) / count(is_correct IS NOT NULL)` | `practice_items` |
| **人均答题** | 答题量 / DAU | 上面两个相除 |
| **平均单题时长** | `avg(time_ms)`，**剔除 0 与 >600s** 的离群值 | `practice_items` |

**★ 三个最容易算错的地方**（都写成用例，见 §7）：

1. **DAU 用"行为"不用"登录"**。`users.last_login_at` / `login_count` 是现成的、算起来最便宜 ——
   但它把"打开就关"也算活跃，会让 DAU 虚高、而且**与答题量不同源**（两个数字对不上时无法解释）。
   → 选行为口径；`last_login_at` 只在"登录趋势"这个**独立**指标里用，且不叫 DAU。
2. **正确率的分母是"已答"，不是"总题"**。`practice_items.is_correct IS NULL` = 未作答（可能只是翻过）。
   混进分母 → 正确率被"没答的题"稀释，且**越是没答完的会话越难看**。
3. **时区必须是 `Asia/Shanghai` 的日界**。表里是 `TIMESTAMPTZ`；
   直接 `date_trunc('day', answered_at)` 用的是 UTC 日界 → **"今日"少算 8 小时（00:00–08:00 归到昨天）**。
   统一写 `(answered_at AT TIME ZONE 'Asia/Shanghai')::date`。

### 2.2 趋势（`trends`）

`metric` ∈ `answers | new_users | active_users | accuracy | avg_duration`，
`granularity` ∈ `day | week | month`。

**★ 必须补空日**：某天没人答题 → `GROUP BY` 直接**不返回那一行** → 折线图**把两天连成一条直线**，
视觉上是"平稳"，实际是"断档"。做法：`generate_series` 生成完整日期轴，再 `LEFT JOIN` 聚合结果，
缺的补 0（`accuracy` 这类比值型补 `null`，前端断线，**不补 0** —— 补 0 会画出"正确率暴跌到 0"的假象）。

### 2.3 分布（`distributions`）

`dim` ∈ `subject | professional | difficulty | type`。
**★ 每个维度都有两个视角，必须分开命名**（混在一起就会得出互相矛盾的结论）：

| 视角 | 问的问题 | 源表 | 例 |
|---|---|---|---|
| **题库结构** | 我们**有多少**题 | `questions` | 各科目题量、难度 1–5 的题数 |
| **作答分布** | 用户**练了哪些** | `practice_items` JOIN `questions` | 各科目被作答次数、各难度**正确率** |

两者不可互相替代：题库里"难"的题占比 20%，不代表用户作答里难的只占 20%（人天然回避难题）。

- 专业维度有**两条路**，也要分开：`subjects.professional`（**课的**专业）vs `user_profiles.professional`（**人的**专业）。
  默认给"**人的**专业 × 作答量"（运营更关心"哪个专业的人练得多"），另一个作为可选维度。
- 字典类（`type` / `difficulty`）的展示名从 `dictionaries` 取（`dict_type='question_type'` 等），**不前端硬编码**。

### 2.4 漏斗（`funnel`）

`注册 → 首次答题 → 付费`。**★ 必须是"同一批人"的留存式漏斗，不是三天的独立日活相减。**

```
注册日 2026-09-01 的这批用户：
  ① 注册            = 这批人里 created_at 落在该日的人数
  ② 首次答题        = 其中 min(答过题的时间) 存在 的人数
  ③ 付费            = 其中存在 status='paid' 的订单 的人数
```

- **按注册日分批**（默认最近 30 天的注册队列），可切换"全部时间"。
- 每一段显示：绝对人数 + **相对上一段的转化率** + 相对第一段的累计转化率。
- `② ` 的判据用 `practice_items.answered_at` 的 `min`，**不是** `practice_sessions` 存在 ——
  开了会话没答题是常见行为，算进去会让第一段转化率虚高。
- 第三段在真实数据里大概率是 0（没有支付环境）—— 造数脚本会给它造（§6），并在图上**标注"演示数据"**。

### 2.5 薄弱点（`weak-points`，附加）

按 `practice_items` 聚出**正确率最低的 N 个知识点**（`knowledge_point_id`，样本数 ≥ 20 才算，
否则"错 1 题 = 0% 正确率"会霸榜）。这是看板里**最可能被真正使用**的一块（教研改题的依据）。

## 3. 接口设计

### 3.1 端点清单

统一前缀 `/api/v1/admin/stats`，全部 `require_permission("stats:read")`，
响应沿用全站信封 `{code, message, data, trace_id, server_time}`。

| 端点 | 参数 | 返回 |
|---|---|---|
| `GET /overview` | — | 4+2 个指标卡：今日值 / 昨日值 / **同比昨日变化** |
| `GET /trends` | `metric`(必) `granularity` `from` `to` `subject_id?` | `{axis:[日期], series:[{name, points:[…]}]}` |
| `GET /distributions` | `dim`(必) `view`(bank\|practice) `from` `to` `subject_id?` | `[{key, label, value, accuracy?}]`，含 `total` |
| `GET /funnel` | `cohort`(30d\|all) `to?` | `{stages:[{key,label,count}], rates:{step:[…], cumulative:[…]}}` |
| `GET /weak-points` | `limit`(默认 10) `min_sample`(默认 20) | `[{kp_id, name, subject, accuracy, sample}]` |

写端点（`?refresh=1` 强制绕过缓存）**不额外开接口** —— 它是查询参数，不引入写权限。

### 3.2 返回结构示例（`trends`）

```json
{
  "code": 0, "message": "ok", "trace_id": "…", "server_time": 1789000000000,
  "data": {
    "metric": "answers", "granularity": "day",
    "from": "2026-08-25", "to": "2026-09-24",
    "axis": ["2026-08-25", "…", "2026-09-24"],
    "series": [{"name": "答题量", "points": [0, 12, 8, "…"]}],
    "meta": {"cached": true, "ttl_sec": 3600, "timezone": "Asia/Shanghai",
             "filled_days": 3, "data_source": "practice_items"}
  }
}
```

★ `meta` 不是装饰：`filled_days` 是**"补了几天空"**（=0 才说明数据是连续的），
`cached/ttl` 让前端能显示"数据截至 xx:xx（缓存）"。**看板最怕的不是慢，是"数字说谎而看不出来"。**

### 3.3 实时 / 聚合 / 缓存：逐端点画线

| 端点 | 聚合方式 | 实时性 | 缓存 TTL | 理由 |
|---|---|---|---|---|
| `overview` | 当日 = 直查原始表；昨日 = 直查 | **真·实时**（当日部分） | **60s** | 当日数字会被反复看；60s 是"感觉实时"与"扛住刷新"的平衡点 |
| `trends` | 直查 + 补空日 + 窗口 | 滞后 ≤ TTL | **1h** | 历史序列**不会因为再看一遍而变化**；1h 是纯收益 |
| `distributions` | 直查（题库）/ JOIN（作答） | 滞后 ≤ TTL | **6h** | 分布是"慢变量"，题库结构一天也不变 |
| `funnel` | CTE + 队列 | 滞后 ≤ TTL | **30min** | 队列口径要跟注册走，变化慢 |
| `weak-points` | 直查 + `HAVING` | 滞后 ≤ TTL | **1h** | 样本门槛决定了它天然平滑 |

**★ 缓存策略的三个决定**：

1. **key 里必须带"筛选条件全集"**：`stats:trends:{metric}:{gran}:{from}:{to}:{subject}` ——
   少带一个参数 = 张三的筛选结果被李四看到（**串数据**，比慢严重得多）。
2. **不做主动失效**：看板全是"读多写少"的公开聚合，**TTL 到期即可**。
   主动失效需要写路径广播（答题时要 bump 缓存），那是 C 端的事，本批引入只会增加耦合面。
   → 例外：`?refresh=1` 手动绕过（运维/演示用）。
3. **Redis 挂了必须降级直连，不能把看板打挂**。`rbac_service.get_privileges` 已经示范过这个形状：
   缓存是**加速器**，不是**依赖**。降级时在 `meta.cached=false` 里如实体现。

### 3.4 聚合策略：v0.1 为什么**不读**预聚合表

`daily_study_stats` 等表是"正确的终局"，但**现在读它 = 读一张空表**（§1.2 无写入方）。
更麻烦的是：**如果本批去写它，就把 C 端的数据职责提前搬进了看板** —— 两处维护必然漂移。

```
v0.1：只读原始表（practice_items / exam_attempts / users / questions）
       —— 数据量小（个人项目 + 造数），响应 < 200ms，够用
切换判据（可判定，不靠感觉）：
       practice_items 行数 > 200 万  或  任一 stats 查询 p95 > 800ms
       → 改为"预聚合表优先 + 回退原始表"，并把写入方明确划给 C 端
```

★ **把判据写死在方案里**，是为了避免"以后有人觉得慢就顺手改成读预聚合表" ——
那会得到一个**口径正确但数据陈旧（且没人更新）**的看板，比慢更难发现。

### 3.5 每个聚合查询都必须带 `statement_timeout`

看板查询天然容易全表扫（`GROUP BY` + 无界时间范围）。按**硬约定 N**：
**无界等待必须加界**。做法：统计专用连接或 `SET LOCAL statement_timeout='3s'`，
超时返回 `503xx`（服务繁忙）而不是把 API 连接池吸干。
—— 这正是`conftest.sql_exec` 那条坑的同一条规则，只是换了个位置。

### 3.6 索引与迁移（走 `db/migrations/`，遵守硬约定 B）

现有索引已覆盖 `questions` 的筛选（`idx_questions_filter` 等）✓。需**新增 3 条**（按查询形态反推）：

```sql
-- 趋势/概览：按日聚合答题
CREATE INDEX idx_practice_items_answered_at ON practice_items (answered_at) WHERE answered_at IS NOT NULL;
-- 漏斗：按用户取首次答题
CREATE INDEX idx_practice_items_user_answered ON practice_items (user_id, answered_at);
-- 队列：按注册日分批
CREATE INDEX idx_users_created_at_alive ON users (created_at) WHERE is_deleted = false;
```

⚠️ `idx_users_created_at` 已存在（`users(created_at DESC)`），但**没有 `is_deleted` 谓词** ——
部分索引能不能替代它，**要用 `EXPLAIN` 实证**（迁移里附上前后 `EXPLAIN` 输出）。
**验证步骤**（硬约定 B）：造迁移前数据 → 跑迁移 → 断言索引存在且被命中 → 再跑一次断言幂等 → 清场。

### 3.7 权限：**零改动**

`stats:read`（`permissions` id=701，`module='stats'`）**已经在 schema 的 RBAC 种子里** ✓，
前端 `P.statsRead` 也已定义 ✓。开工前只需确认它归属哪些角色（种子里它与
`user:read / system:audit / exam:read` 同批授予）；若 `researcher` 也应能看统计，
按 `seed-rbac` 的切片重放即可（**不要手改 schema.sql 的 RBAC 段之外的地方**）。

### 3.8 服务/路由落点（与现有分层一致）

```
apps/api/app/api/v1/admin_stats.py     ← 路由：参数校验 + 权限 + 缓存读取
apps/api/app/services/stats_service.py ← 聚合 SQL（**唯一的口径实现处**）
apps/api/app/schemas/stats.py          ← 响应模型（pydantic）
```

★ 口径**只准出现在 service 一处**：口径散到路由/前端 = 同一个指标两个数，
而看板的"数不一致"是最难被发现的缺陷（没有断言会失败）。

## 4. 页面结构

### 4.1 一个页面，四个区块（不做子页面）

`apps/admin/src/app/(console)/dashboard/page.tsx` —— 单页 + 全局筛选条。

**为什么单页**：个人项目、数据量小、区块之间是**同一次分析的连续视角**（先看总量 → 再看趋势 →
再看结构 → 最后看漏斗）。拆成多页会：① 每次切换都重新拉全量 ② 筛选条件要跨页同步 ③ 导航碎片化。
—— 判据：**区块之间是否需要"带着同一个筛选看另一张图"**？是 → 同页。

```
┌─ 筛选条：时间范围 [近 7 天 ▾] 科目 [全部 ▾] [刷新]  ← 状态全部进 URL query
├─ 区块 1  指标卡 ×6（今日 / 昨日 / Δ）
├─ 区块 2  趋势：折线（可切 metric × granularity），支持同比
├─ 区块 3  分布：科目 [柱] / 专业 [柱] / 难度 [堆叠柱] / 题型 [环]
└─ 区块 4  漏斗：注册 → 首次答题 → 付费（横向漏斗 + 转化率标注）
```

### 4.2 图表清单

| 区块 | 图表 | 类型 | 交互 |
|---|---|---|---|
| 指标卡 | 6 个 | 数字 + 迷你 sparkline（可选） | hover 看口径说明（★ 指标定义要能在界面上看到） |
| 趋势 | 1 个 | **折线**（多 series） | 切 metric / granularity；`dataZoom`（拖时间轴）；断点不连线 |
| 分布 | 4 个 | **柱状** ×2、**堆叠柱** ×1、**环形** ×1 | 点柱子 → 联动筛选 `subject_id` |
| 漏斗 | 1 个 | **漏斗** | hover 显示转化率；队列可切 30d / all |

### 4.3 四种状态都要有（不是只有"成功"）

- **空态**：造数脚本没跑 → 显式提示"没有数据，先跑 `tools/local-verify/seed-stats.py`"，
  **而不是画一堆 0**。
- **加载态**：区块骨架屏（区块独立请求 → 独立 loading）。
- **错误态**：单区块失败不影响其它区块（`react-query` 的 per-query error）。
- **无权限态**：复用现成 `ForbiddenState` ✓；导航项由 `permission.ts` 推导（见 4.4）。

### 4.4 接入现有控制台

- `lib/permission.ts` 的 `MODULE_ENTRIES` **加一行**：
  `{ perm: P.statsRead, href: "/dashboard", label: "统计看板" }`
  —— 位置放在**第一个**（它是"概览"性质，比题库更该当落地页）。
  ⚠️ 这会改变有 `stats:read` 的角色登录后的**落地页** —— 是本批唯一一处"影响现有行为"的改动，需要单独说明。
- 筛选状态放 URL：`/dashboard?range=7d&subject=3&metric=answers` → 可刷新、可分享、浏览器后退有效。

## 5. 图表库选型

| 候选 | 体积（gzip，按需） | React 契合 | **漏斗图** | 大数据量 | 中文生态 |
|---|---|---|---|---|---|
| **Recharts** | ~90–110 KB | ★★★ 原生组件 | ❌ 无 | 一般（>5k 点掉帧） | 一般 |
| **Chart.js** + `react-chartjs-2` | ~70–100 KB | ★ Canvas 命令式包装 | ❌ 无 | 好（canvas） | 一般 |
| **ECharts** + `echarts-for-react`(或自封装) | ~150–200 KB（按需 tree-shake） | ★★ ref + option | ✅ **原生** | ★★★ 好 | ★★★ 中文文档/中文排版 |

### 结论：**ECharts（按需引入）+ 一层薄封装 `<EChart/>`**

**理由（5 条）**

1. **漏斗图是需求，Recharts / Chart.js 都没有** —— 用它们就得拼两个库或自己画梯形，
   而"两个图表库"的体积与维护成本**大于** ECharts 按需引入。
2. **`dataZoom`**：趋势图在手机/窄屏上必须能拖时间轴，ECharts 原生；Recharts 要自己接 brush。
3. **中文场景**：轴标签、tooltip、千分位/百分比格式化、字体在中文环境下的表现，ECharts 是主场。
4. **按需引入可控**：只引 `LineChart/BarChart/PieChart/FunnelChart` + `GridComponent/TooltipComponent/LegendComponent/DataZoomComponent` + `CanvasRenderer`，
   实测体积远低于全量包（本批会把真实 gzip 数字写进验收）。
5. **一个库覆盖全部四种图** —— 少一个依赖、少一套样式约定、少一次"两个库颜色不一致"。

**代价（3 条，都接受）**

1. **命令式 API**：要用 `useRef + useEffect` 管生命周期 → **用一层 `<EChart option={} height={} />` 封装一次性解决**（约 40 行），
   业务组件只传 option，不碰 ref。
2. **SSR/App Router**：ECharts 只能跑客户端 → 用 `next/dynamic(..., {ssr:false})` 包住封装组件（这一层封装正好也是这层边界）。
3. **体积最大**：150–200 KB。**取舍**：这是**内部管理后台**（不是 C 端首屏），
   为了一个功能完整、维护省心的图表库付 100 KB 是划算的；C 端的轻量图表需求应另选（Recharts），**两处不共用**。

**逃生舱**：若最终判断不需要漏斗图、也不要 `dataZoom`，则改用 **Recharts** ——
替换成本被 §5 的封装层挡住（业务组件只依赖 `<EChart option>` 风格接口，换库只改封装 + option 映射）。
**这就是先做封装层的意义：把"选型判断"的可逆性留在自己手里。**

**不选 antd/charts、不选 d3 的理由**：前者会把 antd 整套设计体系拖进来
（现有 UI 是 tailwind + radix，混两套视觉规范反而更贵）；后者**是工具库不是图表库**，
画一个折线要自己写 300 行，与"本批想练的是查询与可视化工程"的目标不匹配。

## 6. 造数脚本（**没有它，看板全是 0**）

`tools/local-verify/seed-stats.py`

- **固定随机种子**（`--seed 42`）→ **跑两遍结果逐行一致**（这是它自己的验收判据）。
- 规模：用户 500（按 90 天分布注册，含 `user_profiles` 完整度差异）、
  练习会话 ~8000、`practice_items` ~12 万、模考 ~600、订单 ~120（其中 `paid` ~40）。
- 分布**刻意造出可被验证的形状**（否则无法判断看板算得对不对）：
  · 周末答题量比工作日低 30%
  · 每隔 7 天有一个**完全没人答题的日子** → 专门验 §2.2 的补空日
  · 难度 5 的正确率显著低于难度 1（真数据也如此）
  · 注册后 3 天内首次答题率 ~65%
  · 付费集中在注册后 7 天内
- **清场**：`--clean` 只删脚本自己造的行（按 `id` 段或 `register_source='seed_stats'` 标记），
  **绝不动 `questions` / `subjects` 等共享种子数据**。
  ⚠️ 这条是从坑 57 的同一个夹具（`created`）那里学来的：**验收脚本不要改共享基础数据**，
  它的破坏**当场不报错**，要在另一个文件的用例里才暴露。
- 幂等：重复执行前先 `--clean`（或检测已存在则拒绝并提示）。

## 7. 验收标准

| # | 标准 | 判据 |
|---|---|---|
| 1 | 接口确定性 | 同一时点连续两次调用（`?refresh=1`），除 `server_time` 外逐字节一致 |
| 2 | 补空日正确 | 指定 7 天区间里有 1 天无数据 → `axis` 仍有 7 项，`filled_days == 1` |
| 3 | 零分母不炸 | 新库（无任何答题）下 5 个端点全部 `code=0`，比值型返回 `null` 而非 `NaN`/`0.00` |
| 4 | 时区正确 | 造一条 `answered_at = 当天 00:30 (+08)` 的答题 → 计入**当天**（而不是前一天） |
| 5 | 漏斗单调 | `count(①) ≥ count(②) ≥ count(③)`，且每段 ≤ 上段（用户级，不可重复计数） |
| 6 | 缓存可观测 | 响应头/`meta` 能区分 hit/miss；改数据后 ≤ TTL 内数字不变、`?refresh=1` 立刻变 |
| 7 | 查询有界 | 人为造 10 万行 + 无界时间范围 → 3s 内返回（超时则 `503xx`），**不挂起** |
| 8 | 门禁不降 | ruff / pytest / tsc / prettier 全绿；**覆盖率 ≥ 93.10**（现门槛）；新增 service 必须有契约测试 |
| 9 | 口径单一 | `grep` 能证明每个指标的口径只在 `stats_service.py` 出现一次 |
| 10 | 前端不做算术 | 前端只格式化，不做任何除法/累加（除法的两端必须是同一个响应的字段） |

## 10. 风险与取舍

| 风险 | 处置 |
|---|---|
| **看板数字与真实数不一致**（最难发现的缺陷） | 口径单点（§3.8）+ §7 的判据 3/4/5 + 造数脚本"刻意可验证的形状"（§6） |
| **缓存串数据**（筛选参数漏进 key） | key 由"参数全集"函数**唯一生成**（一个 `cache_key()` 函数，禁止手拼字符串） |
| **看板拖垮 API** | `statement_timeout` + 独立 `rate_limit` + 缓存；`weak-points` 加样本门槛 |
| **落地页被改**（`MODULE_ENTRIES` 插到第一位） | 单独说明 + 验收时明确"这是有意改变"；如不接受，改为插在**最后**并把落地优先级还给题库 |
| **造数污染共享数据** | `--clean` 按标记删除 + 跑两遍一致 + 清场后 `questions` 计数不变（§6） |
| 图表库选型返工 | 封装层隔离（§5 逃生舱） |
