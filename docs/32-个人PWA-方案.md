# 32 · 个人 PWA 方案（**B：C 端裁剪，不是从零搭脚手架**）

> 用户口径（2026-10-06）：方向 **B → C**；B 的定位是「**C 端裁剪**」——
> UI / 页面结构 / 状态管理 / 路由**直接搬**，**唯一要重写的是数据层**（换成 IndexedDB）。
> **本文零实现。** 所有"事实"都是实读出来的，出处附在每条后面。

---

## 0. 一句话

在 `apps/pwa/` **新起一个独立应用**，把 `apps/web` 的界面**复制**过来，
把 `lib/api.ts` 那一层换成 **IndexedDB**，**零后端、零登录、零网络**；
题库由用户在**首次启动时导入**（一个文件 + 对账）。

> 用户设想：「**从 GitHub 拉 `questions.json`**」。

**走不通**：`data/` **不在 git 里**（`docs/27` §1.5 记过同族事故 —— Render 容器里没有 `data/`，

本文按**前一条**设计（零新增基础设施），并把"托管下载"记成可选增强。

## 2. 用户确认的 6 件事（照单执行）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 目录结构 | **`apps/pwa` 独立**（不条件编译 —— 会让两边都复杂；且 `apps/web` 有自己的 SW/middleware 契约） |
| 2 | UI 复用 | **复制**（不抽包 —— 抽包要动 C 端，风险大、收益低） |
| 3 | 题库来源 | **首次启动导入**（选文件；见 §4） |
| 4 | 持久化 | **只用 IndexedDB**（不上 OPFS） |
| 5 | 砍掉 | **登录 / 注册 / 引导 / 我的-账号**；保留 **答题 / 错题本 / 收藏 / 标记 / 笔记 / 报告** |
| 6 | 数据备份 | **导出 / 导入 JSON，放「我的 → 设置」** —— ★ 硬需求（IndexedDB 会被清缓存） |

### 2.1 ★★ 复制带来的**新风险**（必须有对策）

复制之后，**C 端与 PWA 的同一份 UI 变成两份**：在 C 端修了 bug、PWA 侧**没修**，
而且**不报错**（正是「同一个事实两种写法」那一族）。

⇒ 对策（**机械的，不靠记得**）：
1. `apps/pwa/COPIED-FROM-WEB.md` 列出**每一个复制品的来源路径**（新文件必须登记）；
2. 加一条**门禁**：清单里的每个来源文件与目标文件**要么逐字节相同、要么在清单里注明"有意分叉 + 理由"**
   —— 逐字节相同做不到（数据层必然分叉），所以判据取"**登记 + 有意分叉要写理由**"，
   并且**清单必须覆盖所有复制品**（新复制一个文件不登记 ⇒ 红）。
3. ★★ **"理由"本身必须可判定**（**用户的补充，2026-10-06**）。否则门禁只检查了"有没有字"，
   没检查"这字算不算数"—— 而**什么都能填**的理由等于没有理由。合格的理由要**指名一个具体的依赖或数据差异**：

   | | 写法 | 为什么可判定 |
   |---|---|---|
   | ✅ | `因为依赖 C 端专有模块（middleware.ts / lib/auth-store.ts）` | 去 grep 这两个文件在不在，**有/没有是机械的** |
   | ✅ | `因为数据源不同（API fetch → IndexedDB 读）` | 看源文件里有没有 `request(` / `fetch(` |
   | ❌ | `有意简化` / `暂时这样` / `后续再改` / `先复制过来` | **这些理由能套在任何一个文件上** ⇒ 等于没写 |

   ★ 判据的形式：**每个理由都要能被一条命令验证**（"X 里真的引用了 Y 吗"）；
   **写不出这条命令 ⇒ 理由不合格**。★ 那几个 ❌ 的写法与「以后 / 时机未到」是**同一族**
   （**逃避式表述**）—— 门禁遇到它们应直接判红，而不是放行。

> ★ 这条不是"洁癖"：`apps/pwa` 与 `apps/web` 会**长期共存**，而"下游复制品悄悄落后"
> 是本项目已经踩过两遍的形态（`practice_items.marked` 的语义漂、批次 2 的 B16 判据只覆盖一半）。

### 2.2 ★ SW 与 IndexedDB 的分工（**与 C 端不一样**）

**用户的补充（2026-10-06）**：PWA 的离线能力**来自 IndexedDB，不是 SW**。

| | C 端（`apps/web`） | 个人 PWA（`apps/pwa`） |
|---|---|---|
| 数据来自哪 | **网络**（API） | **IndexedDB**（本机） |
| Service Worker 的职责 | 缓存**静态资源** | **只**缓存**应用壳**（HTML / JS / CSS / 图标 / manifest） |
| 断网还能答题吗 | **不能**（数据要联网） | **能** —— 因为题目与作答都在本机 |

⇒ **`apps/pwa/public/sw.js` 不缓存 `pwa-bank.json`**，也不做"数据请求的运行时缓存"：

- 题库、答题记录、错题、收藏、标记、笔记 —— **全部在 IndexedDB**；
- SW 的唯一职责 = 让**应用壳**能离线打开。

★ 为什么必须把这条**写死**：这是个**容易反着做**的地方 —— 直觉会让人"用 SW 缓存题库"，后果两条
① 13.6 MB 的包被 SW **再存一份**（占双份空间）；
② 换题库时 **SW 与 IndexedDB 各有一份**、互相不一致，症状是「**导入成功了但题目还是旧的**」——**不报错**。
★ 与 §8 判据 6 的关系：**断网能答题证的是 IndexedDB 在干活，不是 SW 在干活**；
  两条要分开验（"壳能打开" ≠ "数据在"），否则"SW 缓存了壳"会把"IndexedDB 是空的"盖住。

## 3. 数据层迁移策略（**本方案的核心**）

### 3.1 一句话：**判分语义只留一处，PWA 是"哑比较"**

从 API 换到 IndexedDB，最大风险不是"存哪里"，而是 **判分/统计的语义出现第二份实现**。
`answer.py` 里那些函数（尤其 `judge_bool` 要处理**两套判断题写法**，见 BL-20）
**不能抄一份到 TS** —— 抄了就是两个可变物，迟早分叉，而症状是"某些判断题在 PWA 里永远判错"。

⇒ 设计：

| 层 | 归属 | 内容 |
|---|---|---|
| **语义**（唯一真相） | **Python 侧** | `canonical_doc` / `judge_bool` / `PARTIAL_CREDIT_RATIO` / `GRADABLE_TYPES` |
| **固化** | 导出时**跑一次** | 把每题 `answer` 归一到唯一写法；把评分规则写进包的 `meta.grading_rules` |
| **执行**（哑） | PWA 侧 | 只做「**集合相等**」+ 读 `meta.grading_rules`（不自带任何阈值/特例） |

⇒ PWA 侧**没有独立语义**，因为它没有可"决定"的东西：判断题写法已在导出时归一，
部分分阈值来自包。（这条判据值得写进代码注释：**PWA 的判分函数不许出现字面量规则**。）

### 3.2 导出包（新增一个脚本，不新增基础设施）

`tools/pwa/export-bank.py`（在 Python 侧跑一次）：

```jsonc
{
  "meta": {
    "schema_version": 1,            // PWA 据此拒绝不认识的包
    "bank_version": "<fingerprint>",// 来自 import_manifest.json
    "exported_at": "...",
    "totals": {"questions": 6000, "options": 20156, "knowledge_points": 52},
    "by_subject": {...}, "by_type": {...}, "by_difficulty": {...},
    // ★ 下面两个值**实测**自 `practice_service.py`（`:109` / `:48`）——
    //   导出时写进包是**把唯一真相随包下发**，不是在这里再定义一遍。
    "grading_rules": {"partial_credit_ratio": 0.5, "gradable_types": ["single","multiple","judge"]}
  },
  "questions": [ /* 归一后的题；去掉 PWA 用不到的字段（material_html/parent_id/root_id/…） */ ]
}
```

★ 用户**只需要上传这一个文件**（不用同时管 `questions.json` 与 `import_manifest.json`）。
★ 代价：多一步"跑脚本"。**收益**：评分规则与答案写法**只有一处定义**。
★ 可选增强（本文不做，记 BL）：把包托管到 `apps/web/public/` 之类，让 PWA 直接下载 —— 
   但那是"给公开仓库塞 13 MB 二进制"，要单独评估。

### 3.3 IndexedDB 形状（表 → object store）

| 原表 | store | keyPath | 需要的 index |
|---|---|---|---|
| `questions`（+ `question_options` 内联） | `questions` | `id` | `subject_id` / `chapter_id` / `type` |
| `subjects` / `chapters` / `knowledge_points` | 同名 | `id` | `subject_id`（chapters） |
| `wrong_questions` | `wrong` | `question_id` | `subject_id` + `last_wrong_at` |
| `favorites` / `question_marks` | `favorites` / `marks` | `question_id` | `created_at` |
| `notes` | `notes` | 自增 `id` | `question_id` / `subject_id` / `created_at` |
| `practice_sessions` | `sessions` | `id` | `started_at` |
| `practice_items` | `items` | `[session_id, seq]` | `session_id` |
| （新） | `meta` | `key` | —— |

★ 三条**红线**（都是项目已有约定，别在 PWA 里丢掉）：
1. **日界一律 `Asia/Shanghai`** —— "今天答了几题 / 连续天数"必须按这个时区算，
   否则跨零点或用户改时区就会错（**不给解释**）。
2. **零分母返 `null`**，不是 `0`（正确率那类除法）。
3. **软删要过滤** —— `notes.is_deleted`、`wrong.is_removed` 在**每条读路径**上都要带；
   漏一处 ⇒ "删了还在"，**不报错**。

★ **ID**：PWA 单机 ⇒ 自增 / `crypto.randomUUID()` 即可；
但**题目 id 沿用包里的字符串**（保持与 C 端一致，将来"导出到 C 端"才可能）。

### 3.4 报告：**知识点分布要做**（**用户的补充，2026-10-06**）

**先纠正本方案上一版的判断**：上一版把"按知识点"划进了"报告简化的可选项"。用户口径：
> "报告简"不是问题，"报告**少一个核心维度**"才是。知识点分布**不依赖对齐** —— 导入包里就有
> 知识点数据，PWA 自己 `GROUP BY` 聚合很简单。

⇒ 定稿：报告**必含五个维度** —— 答题数 / 正确数 / 正确率 / **按科目** / **按知识点**。
- 知识点数据从哪来：`questions.knowledge_point_id`（导出包已内联）→ 按 `knowledge_point_id` 分组算正确率；
- 聚合口径（分母是"做过的题"还是"答对次数"）**照 §3.1 的做法**：口径随包下发（`meta`），
  PWA 只执行、不自带阈值；
- **零分母一律返 `null`**（红线 2）—— 某个知识点一道没做过时显示 `—` 而不是 `0%`。

**剩下的是"对齐"问题，不是"做不做"问题**：与 App 版**逐位一致**才需要单独一批（同 §3.1 的下沉做法）。
页脚那行差异说明**只写真实差异**，不许把已做的维度写成"不含"。

## 4. 首次启动引导（用户怎么把题库放进去）

```
/setup  →  ① 选文件（<input type="file" accept=".json,.gz">）
        →  ② 读 → 校验 meta.schema_version
        →  ③ **分批写** IndexedDB（每 500 题一个事务）+ 进度条 + 可中断续传
        →  ④ **对账**（见下）→  ⑤ 写 meta.bank_version → 进主界面
```

**对账（必做，且要能证伪）**：用包里的 `meta` 逐项比 ——
`题目数 == 6000`、`选项数 == 20156`、`by_subject` / `by_type` 分布**逐项相等**。
不一致 ⇒ **不进主界面**，并显示"哪一项差多少"（照做的提示，不是"导入失败"四个字）。
★ 为什么必须对账：**半份题库**的症状是"某些科目题很少 / 某些题搜不到"，
**不会报错** —— 而对账能把它变成一条明确的红。

**三条实现约束**：
1. **导入必须可重入**：中途关页面 ⇒ 下次进来要么"继续"要么"重头"，**不许留下半份数据**
   （判据：写数据前先写 `meta.importing=true`，全部完成后才清；启动时见到 `importing=true`
   就**先清空那批再重来**）。
2. **大文件不许卡死 UI**：13.6 MB 一次性 `JSON.parse` 会冻结几秒 ⇒ 用 Worker 或分片解析。
3. **空态要能进**：没题库也能打开 / 安装（`/setup` 是首页），否则"装不上、也就没有 PWA"。

### 4.1 ★★ 已经导过题库，又导新包 ⇒ **换题库 = 清空所有数据**（**用户的补充，2026-10-06**）

**"可重入"（约束 1）只覆盖"同一个包导一半"，不覆盖"换一个包"** —— 这是两件事。
换包时 `question_id` 可能对不上（新包的题集不同），旧的答题记录 / 错题 / 收藏 / 标记 / 笔记
会**指向不存在的题** ⇒ 界面上表现为**空题干行**或**点开报错**，而且**不报错**。

⇒ 定稿行为：

```
/setup（已有题库时）→ 显示 "当前题库：v<指纹>（<N> 题，导入于 <时间>）"
                    → 用户选新文件 → 读出新包的 meta
                    → 【自动判断】
                       · 指纹相同  ⇒ 提示"这就是当前题库"，只提供「重新导入」/「取消」
                       · 指纹不同  ⇒ ★ 二次确认框：
                                       "当前题库 vX（<N> 题）
                                        准备换成   vY（<M> 题）
                                        换题库会【清空你的全部数据】——
                                        答题记录 / 错题本 / 收藏 / 标记 / 笔记都将消失，且无法恢复。
                                        【建议先到「我的 → 设置 → 导出全部数据」备份】
                                        [取消]  [清空并导入]"
                    → 确认后：清空全部 store（含 meta）→ 走 §4 的正常导入流程
```

**三条硬要求**：
1. **必须二次确认**，且确认框里**写清"清空哪些东西"**（不是"确定要换吗"）。
2. **必须提示备份**（§7 的导出口就在那儿；这是"清缓存就没了"之外的第二个数据丢失入口）。
3. **`question_id` 对不上时不许"尽量保留"** —— 那会造出**指向不存在题的行**；
   宁可清空（用户已确认过），也不要留下"半截数据"。★ 这与约束 1 的"不许留下半份数据"是同一条原则。

#### 4.1.1 ★ 约定 T 在 PWA 里的**边界**（2026-10-07 补，用户裁定）

约定 **T**（*「我的内容」不随「平台内容」的生命周期变化*）说的是**平台内容变化**。在 PWA 里这条必须写清边界，否则会被读成"PWA 也保证换题库后记录仍在"—— **那是假话**：

| | C 端（有后端） | PWA（单机） |
|---|---|---|
| "平台内容变化"的形态 | 题被**下架**（`unpublish` / 归档）⇒ 记录仍在、题标「已下架」 | ⚠️ **没有"题下架"这个操作** —— 用户的库是**一份快照**，没有服务端去改它 |
| 唯一让题消失的途径 | 下架 | **换题库** |
| 那算不算"平台内容变化"？ | 算 | **不算** —— 换题库 = **换掉平台**（连同这个平台的用户数据一起换），是用户**主动**的清空，不是平台单方面改了内容 |

⇒ 所以 §4.1 的「换题库 = 清空所有数据」与约定 T **不冲突**：T 要保护的是"**平台**改内容时别弄丢我的东西"，
而换题库是"**我**换了一个平台"。
★ **代价（如实写）**：PWA 里 `question_available=false` 这一态**没有写入路径**（硬约定 **F**：状态"可达" ⟺ 有任何接口能写入它）
⇒ 走查里那条"题不在了、记录仍在"只能用**导入一份"点名的题已不在库里"的备份**来构造
（`tools/pwa/e2e-pwa.py` 的 `loop` 场景 ⑦；报告里已明说它**不是**换题库，没假装）。
★ 想改成"换题库也保留" ⇒ 见 **`docs/21` BL-30**（触发条件 / 方案要点 / `content_hash` 边界都在那条里，**别在这里重新设计**）。

### 11.1 ★★ 一个架构决定：**只让一个文件分叉**

方案 §2.1 说"复制带来的风险是下游悄悄落后"。B-1 把这件事压到最小，做法是：

> **`apps/pwa/src/lib/api.ts` 把 C 端那套 `request<T>(path, opts)` 的形状架在 IndexedDB 上。**

于是**页面可以逐字节复制** —— 需要人工维护分叉的只剩**一个文件**。

| | 数量 |
|---|---|
| 逐字节相同（sha256 相等） | **17** |
| 有意分叉 | **8**（含 `api.ts` / `sw.js` / 两个 layout / 包配置） |
| 只在 PWA 存在 | **3**（`db.ts` / `grade.mjs` / `setup/page.tsx`） |

★ 被复制过来的两个**核心页面**（答题页 41.9 KB、结果页 9.1 KB）**一个字节都没改**。

**代价（如实写）**：`api.ts` 要"演一遍后端"（13 个路由），而它演得对不对需要判据。
判据之一就是 `不变量 12` 里那条"**本文件里不许出现 `fetch(`**"——
它把"数据源确实换了"这件事变成一条机械检查，而不是一句承诺。

### 11.2 判分对拍（§8 判据 1）—— **12557 条逐条相同**

```
[4/4] 比对
  ✓ 判分结论与得分**逐条相同**（12557 条）
  ✓ 用户答案的归一并列相同（12 条，其中 6 条是「该拒」的）
  ✓ 声明的 2 条差异仍在（判断题标号写法：后端宽容 / PWA 只认布尔）

  反向对照（旧写法 [A] vs 用户 [true]）：
    Python（有 token 映射）= True / 1.0
    PWA  （哑比较）        = False / 0
    ✓ 两侧**不同** —— 归一这一步确实在承重。
```

向量 = 每道**可判分**题（3049 single + 1501 multiple + 978 judge）×｛全对 / 全错 / 半对｝。

**★★ 那两条"声明的差异"是刻意留的，不是漏修。** 后端 `normalize_user_value` **宽容**
判断题的标号写法（`"A"` / `"对"`），理由是"库里有种子那一套写法，测试与脚本很可能照着库里的发"。
PWA **不宽容**，因为：
1. 它读的包在**导出时已经归一**（`export-bank.py` 用 `check_doc()` 把关，没归干净不导出）
   ⇒ **不存在旧写法的来源**；用户答案的唯一生产者是界面，发的是布尔；
2. 要宽容就得在 JS 里放一张 `JUDGE_TRUE_TOKENS` 表 = **第二份语义**，正是 §3.1 禁止的。

⇒ 对拍脚本把这两条**断言为"必须不同"**：哪天有人给 JS 补上宽容，它会当场红。

**第三条断言（反向对照）才是这个脚本的价值所在**：它证明"导出时归一"这道闸**在承重**。
没有它，把 `check_doc` 那道闸拆掉，上面 12557 条**照样全绿**（向量本来就是照"已归一"造的）。

### 11.4 B-1 新踩的坑（都是"看着对、实际不报错"那一族）

1. ★★ **块注释里的 `*/` 会提前结束注释**（同族：坑 103「注释里的东西也是内容」）。
   我在 `tsconfig.json` 的注释里写了那个 glob 的字面形状，而它含 `**` 紧跟 `/`
   ⇒ 注释在那一处就被**提前结束**了，剩下的文字变成语法垃圾。
   症状：prettier 报 `Unexpected token (22:13)`、`next lint` 抛 TS 内部断言。
   **判据：块注释里不要写"星号紧跟斜杠"的字符序列**（glob / 通配符最常见）。
2. ★ **`JSON` 不支持注释，但 `tsconfig.json` 支持** —— 而这两件事**取决于读它的是谁**
   （TS 用 JSONC 解析器、prettier 按文件名推断）。同一份文件被两个解析器读，
   症状是**一边过一边炸**（同族：坑 93）。
3. ★★ **同一份事实写两遍（人读的表 + 机器读的 JSON）会各说各话** ——
   变异验证当场抓到：只改**表格**时"理由不合格"那条判据**不红**（它读的是 JSON）。
   ⇒ 修法不是"多写一条对账"，而是**让清单是生成的**（`gen-copied-manifest.py --check`），
   于是"改理由"只能改**生成脚本里的表** —— 理由**只有一处**（同族：不变量 8）。
4. ★ **`await` 不能写在非 `async` 的 `.map()` 回调里** —— `tsc` 会报，但报的是
   "Expected 1 arguments, but got 2" 这种**指向别处**的消息（因为 `await` 被解析成了别的形状）。
5. ★ **Windows 上 ESM 动态 `import()` 必须用 `file://` URL** —— 直接传 `C:\...` 会报
   `ERR_UNSUPPORTED_ESM_URL_SCHEME: Received protocol 'c:'`。
   这条**只在 Windows 上炸**（Linux/macOS 的路径本身就是 `/…`）⇒ 用 `pathToFileURL` 显式转，
   不赌平台。
