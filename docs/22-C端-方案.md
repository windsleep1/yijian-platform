## 2. 目录结构：**`apps/web`**

### 2.1 为什么不叫 `apps/c`

| 理由 | 说明 |
|---|---|
| **`web` 才是 C 端的本义** | 用户直接访问的那个 web 站 = C 端；`admin` 是内部后台。`docs/05` 当初写下 `apps/web` 指的就是它 |
| **单字母目录名易混** | `apps/c` 与 `apps/api` 在 `import` 路径、CLI、`ls apps/` 里都只差一个字符，**而它们一个是前端一个是后端** —— 这种混淆不会报错，只会让人找错文件 |
| 与既有命名同族 | `admin` / `api` 都是**语义名**，突然出现一个 `c` 是风格断裂 |

### 2.2 目标结构

```
apps/
├─ api/     FastAPI 后端                    （已有）
├─ admin/   B 端后台（Next.js 14）            （已有）
└─ web/     C 端学员端（Next.js 14 + PWA）    ← 本批新增
```

### 2.3 顺带要做的（否则文档又和现实对不上）

- `docs/05` 的目录树：把 `apps/web/` 那两行改成 `apps/admin/`，并**新增** `apps/web/` 一行。
- `docs/02` §3.1 的 49 页清单**不动**（它是规划，不是当前状态）。
- ⚠️ 记一条：`docs/05` 的树是 **2026-09-1x 的规划快照** ——
  与其让读者去猜"哪个才算数"，不如**在树顶端加一句"本树以当前仓库为准，规划见括号"**。

## 3. 与 `apps/admin` 怎么共享

### 3.1 现状：**没有任何 workspace 机制**

```
$ ls package.json pnpm-workspace.yaml turbo.json
（都没有）      ← apps/admin 是独立 npm 项目，CI 里就是 `cd apps/admin && npm ci`
```

### 3.2 结论：**首批不共享**（除 §9 的 `api.ts` 复制）

**不共享 UI 组件 —— 这次是"负收益"，不是"以后再说"**：

| | B 端 admin | C 端 web |
|---|---|---|
| 布局 | 侧边栏 + 宽表格 + 抽屉 | 底部 Tab + 单栏 + 全屏手势 |
| 密度 | 一屏塞下 20 行 | 一屏 1 道题 |
| 最小可点 | 28~32px | **44px**（docs/02 §2.2） |
| 数据量 | 分页表格 | 单条详情 |

⇒ 两端的组件**看起来像、约束是反的**。强行共用会得到一个"两边都不合适"的中间态，
**比各写一份更贵**（这正是 `apps/admin` 里那些组件注释反复在说的事）。

### 3.3 抽包的触发条件（按硬约定 P，可判定）

> **当同一个文件必须在两个 app 里各改一次时**，就抽出 `packages/shared` +
> 引入 pnpm workspace，而不是继续复制。

**为什么不是现在抽**：现在只有 1.5 个前端（C 端还不存在），抽包要改 CI 的安装步骤、
两个 app 的 tsconfig 路径映射、以及构建缓存 —— 那是**为不存在的复用付构建成本**
（同 `docs/15` 里"没有消费方的字段"那条）。
**但例外是 `lib/api.ts`** —— 它的 3 处逻辑**必须立刻一致**，所以它的处理方式见 §9.2。

## 6. 接口：哪些能复用、哪些必须新增

### 6.1 能直接复用的：**只有 7 个**

```
POST /auth/register            POST /auth/login/password      POST /auth/login/sms
POST /auth/sms                 POST /auth/logout              POST /auth/refresh
GET  /auth/me
```

### 6.2 ★ 其余 49 个**一个都不能复用**，而且**不能"改造"**

最有代表性的是 `/admin/questions/{id}`：

> **它会返回 `answer`（正确答案）与 `analysis`（解析）。**

而 `docs/04` §2.8 对 C 端题目的要求是「**未作答不返答案**」。

⇒ 所以"给 C 端加个 `?client=1` 之类的开关"是**错的**：
一旦同一个接口既能返答案又能不返答案，那么"什么时候不返"就成了一个**参数级**的判断，
而**参数是调用方给的** —— 等于把"不泄题"寄托在考生自己老实。
**必须是两个接口**（读路径只留最外层一处可见性判断，硬约定 A）。

同类不能复用的还有：
- `/admin/chapters/tree` 带的是**管理视角**的章节树（含题量统计、含已下线）；
  C 端要的是"**含我的进度**"的树（`docs/04` §2.4 的 `GET /subjects/{id}/chapters`）。
- `/admin/users/*` 是**管别人**的，C 端 `/users/me/*` 是**管自己**的 —— 后者必须从 token 取 `user_id`，
  **绝不接受请求体里的 user_id**（否则就是一个水平越权洞）。

### 6.3 首批需要新增的接口（约 13 个）

| # | 方法 | 路径 | 用途 |
|---|---|---|---|
| 1 | GET | `/subjects` | 科目列表（`docs/04` §2.4） |
| 2 | GET | `/subjects/{id}/chapters` | **含我的进度**的章节树 |
| 3 | PUT | `/users/me/profile` | 引导：写报考科目/专业/目标分 |
| 4 | GET | `/users/me/profile` | 引导回显 |
| 5 | POST | `/practice/sessions` | 创建练习（首批只支持 `mode=chapter`） |
| 6 | GET | `/practice/sessions/{id}` | 断点恢复（**含已答与答案**） |
| 7 | POST | `/practice/sessions/{id}/answer` | **提交单题 → 判分 + 答案 + 解析**（幂等） |
| 8 | POST | `/practice/sessions/{id}/finish` | 结束练习 → 报告 |
| 9 | GET | `/practice/sessions/{id}/result` | 练习报告 |
| 10 | GET | `/practice/sessions/{id}/wrong` | 本次错题 |
| 11 | GET | `/practice/history` | 做题记录（首页"继续练"用） |
| 12 | GET | `/wrong-questions` | 错题本列表（只读） |
| 13 | GET | `/questions/filters` | 章节练习配置页的筛选项（题型/难度） |

**表结构已经在了**（`practice_sessions` / `practice_items` / `user_question_state` /
`wrong_questions` / `question_stats` —— 见 `docs/03`），所以这批是**纯接口 + 前端**，
不需要新 migration。⚠️ 但**上线前要确认这几个表的实际列**（`docs/03` 是设计稿）。

### 6.4 ★ 你举的 `/me/dashboard`：规划里有，但**首批不加**

`docs/04` §2.2 里它的正式名字是 **`GET /users/me/dashboard`**
（"首页聚合：倒计时 + 今日任务 + 续学 + 掌握度"）。

**建议首批不加**，理由：这 4 块内容**每一块都依赖一个还没有数据来源的子系统**
（倒计时依赖考期配置、今日任务依赖学习计划、掌握度依赖 `user_knowledge_stats`）。
先加接口 = 先写一个**返回半空对象的聚合**，然后前端要为一堆 `null` 写兜底分支
—— 与 `docs/20` S3"等真实数据"是同一个判断。

**触发条件**：**当首页真要放"倒计时 / 今日任务 / 掌握度"这三块时**，
与它们各自的数据来源**同批**加（而不是提前加壳）。

### 6.5 ★★ 一条真实的安全边界（C 端上线前必须处理）

`docs/04` §1.3 写的是：

> 管理端接口额外要求 header `X-Admin-Token`（二次校验，**防止 C 端 token 越权访问后台**）

**而这条在后端没有实现。** 现在的隔离**只有权限码**：

- ✅ 好消息：`student` 角色**没有任何 `question:*` 权限**，实测访问 `/admin/*` 返回 `40301`
  （`tests/test_admin_v4.py::test_question_permission_wall` 钉着这条）；
- ❌ 坏消息：这道隔离依赖"**角色配置一直是对的**"。
  一旦有人给某个 C 端账号（或某个新角色）授了任意一个 `admin` 模块的权限码，
  他就**直接进得了后台接口** —— 而这是**C 端特有的新风险面**：
  B 端只有内部账号，C 端是**任何人都能注册**。

**建议（首批一起做，成本很低）**：
在 `require_permission` 之外加一道**显式的"这是管理端请求"校验** ——
要么实现文档里的 `X-Admin-Token`，要么在 `/admin/*` 的路由级加
"调用者的角色必须是 B 端角色"（白名单）。
**判据**：*把一个纯 C 端账号授上 `question:read`，它还能不能读后台？* ——
现在的答案是"能"，这就够了。

## 7. 移动端优先：设计约束

**直接沿用 `docs/02` §2.2 的那张表**（44px / 48px / 60px 滑动阈值 / 5 列答题卡 / 字号 16-15 /
深色模式 / 断网提示条）。这里只补**实现层**会踩的几条：

| # | 约束 | 为什么 |
|---|---|---|
| 1 | 高度用 **`min-h-dvh`**，不用 `100vh` | 移动端浏览器地址栏收放时 `100vh` 不变 → 底部 Tab 被顶出屏幕 |
| 2 | 底部 Tab **不要用 `position: fixed`** 硬钉 | iOS 键盘弹出时 fixed 元素会错位；用 `dvh` + 布局流 |
| 3 | 底部安全区 `env(safe-area-inset-bottom)` | 全面屏手势条会盖住 Tab 与主按钮 |
| 4 | `touch-action: pan-y` + **禁双击缩放**（答题页） | 双击缩放会与"连点选项"冲突，且考场上误触很致命 |
| 5 | 主页 `orientation: portrait`（manifest） | 只有视频页横屏（`docs/02` §2.2 已定） |
| 6 | 主题色 `#C8102E` | 与 manifest / 徽章一致，别再造一个红 |
| 7 | **滑动切题与系统返回手势会打架** | 边缘 20px 内不响应滑动；阈值 60px 是 `docs/02` 定的 |

## 8. PWA 边界：首批**只做"可安装"**

### 8.1 首批做

1. `manifest.webmanifest`（`docs/02` §2.3 已经写好，直接抄）+ 图标 192/512（maskable）；
2. **一个最小 SW**：只缓存静态资源（JS/CSS/字体/图标），**不缓存接口**；
3. 断网提示条（`docs/02` §2.2 已有规范）：只说"当前离线"，**不说"已存 X 题待同步"**
   ——因为首批没有同步队列，那句话会是假的。

### 8.2 为什么不连"离线答题"一起做（4 条**具体**成本，不是"以后再说"）

| # | 成本 | 说明 |
|---|---|---|
| 1 | IndexedDB 队列 | 离线期间的作答要按序暂存，键是 `session_id` —— 这套还得处理"队列里已经有同一题的两份答案" |
| 2 | Background Sync | 兼容性参差（iOS Safari 长期不支持），必须有"回到前台手动重放"的兜底 |
| 3 | ★ **服务端要接受"补交"，而它的语义现在没定义** | 离线时用户可能已经"结束练习"、session 可能已过期、"今天"可能已经翻页（`daily` 模式按天唯一）。**这些冲突怎么合并，是一个产品决策，不是一个前端功能** |
| 4 | ★ **客户端判分不可信** | 离线时为了给即时反馈，只能客户端判分；但服务端接收补交时**必须重判** ⇒ 用户离线看到的"对/错"可能与最终结果不同。**这个不一致要不要展示、怎么展示，还没定** |

⇒ 结论：**离线答题的前置是服务端的"补交/重放"语义**，而那是 C 端第二批的事。
先做"可安装"，收益（图标、全屏、不跳浏览器）几乎零成本拿到。

### 8.3 触发条件（按硬约定 P）

> **当有真实用户报告"工地上没信号刷不了题"时**，才做离线答题 ——
> 而且它**必须与"服务端补交语义"同批**，不能拆开（拆开就等于先上一半）。

### 9.1 与 admin 一致的部分（**必须**）

|---|---|

### 9.2 `lib/api.ts`：**复制，不抽包**（但有三处必须逐字一致）

`apps/admin/src/lib/api.ts` 有 343 行，其中**大半是注释** —— 而注释里是踩过的坑。
**直接复制它**（§3.3 的抽包触发条件还未到），但要在两端文件顶部互指，并钉住这 3 条：

| # | 必须一致的行为 | 不一致的后果 |
|---|---|---|
| 1 | **401 单飞刷新**（并发 401 只发起一次 `refresh`，其余等同一个 Promise） | 后端是 **Refresh Token Rotation**；三个请求各自刷新 → 第二个到达时旧 token 已作废 → **用户莫名被踢** |
| 2 | 刷新后**把新的 `refresh_token` 存回** | Rotation 是"旧换新"，不存回 → **下一次刷新必失败** |
| 3 | `RETRYABLE_AUTH_CODES = {40100,40101,40104,40105}` / `FATAL = {40102}` | `40102`（签名无效）刷一百次也没用，而"不重试"**不等于"不跳登录"** |

⇒ 这三条**任何一条两边不一致，就等于两边各踩一次同一个坑**。
**所以它的抽包触发条件比别的文件更早**：**第一次需要修改这三条中的任意一条时**，就抽包。

### 9.3 token 存哪：首批沿用 `localStorage`

与 admin 一致（`apps/admin/docs/B端联调坑.md` 第 15 条：那是**取舍留痕，不是 bug**）。
C 端沿用可以**只维护一套刷新逻辑**。

⚠️ 但要记一条待办：**C 端是否迁 `httpOnly` cookie** ——
C 端是**任何人都能注册**的面，XSS 的影响面比 B 端大。
**触发条件**：上线前的安全评审，或**出现第一个用户可自由输入的富文本展示位**时。

> ⚠️ **顺带发现的第三处"文档说 A、现状是 B"**：`docs/04` §1.3 的表格写
> `refresh_token` 存 **httpOnly Cookie 或安全存储**，而 `apps/admin` 实际存在 **localStorage**
> （坑 15 记的是"取舍留痕"）。⇒ 这不是 bug，但**文档里的"httpOnly Cookie"是一个从未落地的选项**。
> 建议：要么把那一行改成"当前实现：localStorage（见坑 15）"，要么把它明确标成**目标态**。
> **别留着一个读起来像"已经是这样"的规划句**（这正是本方案 §1.1 那条要消灭的东西）。
