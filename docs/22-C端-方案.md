## 2. 目录结构：**`apps/web`**

### 2.1 为什么不叫 `apps/c`

| 理由 | 说明 |
|---|---|
| **`web` 才是 C 端的本义** | 用户直接访问的那个 web 站 = C 端；`admin` 是内部后台。`docs/05` 当初写下 `apps/web` 指的就是它 |
| **单字母目录名易混** | `apps/c` 与 `apps/api` 在 `import` 路径、CLI、`ls apps/` 里都只差一个字符，**而它们一个是前端一个是后端** —— 这种混淆不会报错，只会让人找错文件 |
| 与既有命名同族 | `admin` / `api` 都是**语义名**，突然出现一个 `c` 是风格断裂 |

### 2.2 目标结构

```
apps/
├─ api/     FastAPI 后端                    （已有）
├─ admin/   B 端后台（Next.js 14）            （已有）
└─ web/     C 端学员端（Next.js 14 + PWA）    ← 本批新增
```

## 3. 与 `apps/admin` 怎么共享

### 3.1 现状：**没有任何 workspace 机制**

```
$ ls package.json pnpm-workspace.yaml turbo.json
（都没有）      ← apps/admin 是独立 npm 项目，CI 里就是 `cd apps/admin && npm ci`
```

### 3.2 结论：**首批不共享**（除 §9 的 `api.ts` 复制）

**不共享 UI 组件 —— 这次是"负收益"，不是"以后再说"**：

| | B 端 admin | C 端 web |
|---|---|---|
| 布局 | 侧边栏 + 宽表格 + 抽屉 | 底部 Tab + 单栏 + 全屏手势 |
| 密度 | 一屏塞下 20 行 | 一屏 1 道题 |
| 最小可点 | 28~32px | **44px**（docs/02 §2.2） |
| 数据量 | 分页表格 | 单条详情 |

⇒ 两端的组件**看起来像、约束是反的**。强行共用会得到一个"两边都不合适"的中间态，
**比各写一份更贵**（这正是 `apps/admin` 里那些组件注释反复在说的事）。

### 3.3 抽包的触发条件（按硬约定 P，可判定）

> **当同一个文件必须在两个 app 里各改一次时**，就抽出 `packages/shared` +
> 引入 pnpm workspace，而不是继续复制。

**为什么不是现在抽**：现在只有 1.5 个前端（C 端还不存在），抽包要改 CI 的安装步骤、
两个 app 的 tsconfig 路径映射、以及构建缓存 —— 那是**为不存在的复用付构建成本**
（同 `docs/15` 里"没有消费方的字段"那条）。
**但例外是 `lib/api.ts`** —— 它的 3 处逻辑**必须立刻一致**，所以它的处理方式见 §9.2。

## 6. 接口：哪些能复用、哪些必须新增

### 6.1 能直接复用的：**只有 7 个**

```
POST /auth/register            POST /auth/login/password      POST /auth/login/sms
POST /auth/sms                 POST /auth/logout              POST /auth/refresh
GET  /auth/me
```

### 6.2 ★ 其余 49 个**一个都不能复用**，而且**不能"改造"**

最有代表性的是 `/admin/questions/{id}`：

> **它会返回 `answer`（正确答案）与 `analysis`（解析）。**

而 `docs/04` §2.8 对 C 端题目的要求是「**未作答不返答案**」。

⇒ 所以"给 C 端加个 `?client=1` 之类的开关"是**错的**：
一旦同一个接口既能返答案又能不返答案，那么"什么时候不返"就成了一个**参数级**的判断，
而**参数是调用方给的** —— 等于把"不泄题"寄托在考生自己老实。
**必须是两个接口**（读路径只留最外层一处可见性判断，硬约定 A）。

同类不能复用的还有：
- `/admin/chapters/tree` 带的是**管理视角**的章节树（含题量统计、含已下线）；
  C 端要的是"**含我的进度**"的树（`docs/04` §2.4 的 `GET /subjects/{id}/chapters`）。
- `/admin/users/*` 是**管别人**的，C 端 `/users/me/*` 是**管自己**的 —— 后者必须从 token 取 `user_id`，
  **绝不接受请求体里的 user_id**（否则就是一个水平越权洞）。

### 6.3 首批需要新增的接口：**9 个**（初版写 13，自审后砍掉 4 个）

> **本表 = 2026-09-26 修订版。** 初版列了 13 个，按用户提的判据
> "**如果里面有'为了前端方便而加'的，可以让前端组合现有接口 —— 少加接口 = 少一处维护**"
> 逐个自审，砍掉 4 个（见 §6.3.2）。**"为了前端方便"不构成新增接口的理由。**

### 6.5 ★★ 管理端显式隔离 —— **裁定：做，而且首批做**（用户 2026-09-26）

判据（保留）：***把一个纯 C 端账号授上 `question:read`，它还能不能读后台？*** ——
现在的答案是"**能**"。**权限码是"能力"，`/admin/*` 要的是"身份"**：
"这是管理端会话"不能由"你恰好有某个权限码"推出来。

#### 6.5.1 现状（实测量化）

- ✅ `student` 角色没有任何 `question:*` 权限，访问 `/admin/*` 返回 `40301`
  （`test_admin_v4.py::test_question_permission_wall` 等 3 条用例钉着）；
- ❌ 这道隔离**只依赖"角色配置一直是对的"**；
- ❌ `docs/04` §1.3 要求的 `X-Admin-Token` **全仓不存在**
  （`grep -rn "X-Admin-Token"` 只命中 `docs/`，零实现）。

#### 6.5.2 你的设计 → 我的两处修正

> **你的设计**：管理端登录额外发 `admin_session_id`（**存 Redis**，TTL 同 access_token）
> → `/admin/*` 必须带 **`X-Admin-Session: <id>`** → 校验"有权限码 **且** 会话有效"
> → C 端登录不发放。

**修正 ①：不用 Redis、不加 header —— 用已经存在的 `user_sessions`。**

会话**早就在 PG 里**，而且 token 里已经带了它的主键（JWT 的 `sid`）：

```
user_sessions(id, user_id, refresh_token, platform VARCHAR(24), expires_at, revoked_at, ...)
                                            ↑ 登录时 (platform or "h5") —— **这一列已经有了**
apps/admin 登录时已经在传 platform: "pc"     ← auth-context.tsx:66（实测）
```

理由四条：
1. 会话**已经在 PG** —— Redis 再存一份 = **两份真相，TTL 还要同步**；
2. **Redis 抖动会把人踢出后台** —— 而 `api.ts` 注释里刚为 `50003` 写过
   "Redis 抖一下全站用户都被踢出去"的判据（同一个坑没必要再挖一次）；
3. 复用 `platform` 列，**零 migration**；
4. `X-Admin-Session` 与 token 里的 `sid` 是**同一个值** —— 多带一个 header 只是多一个
   "两边不一致"的故障模式（性质同 §9.2 那三处）。

**修正 ②：`platform` 是客户端申报的，服务端只能当"申请"，不能当"事实"。**

否则 C 端客户端自己传 `platform: "pc"` 就绕过去了。⇒ 登录时把 `platform='pc'` 当
**申请管理端会话**，服务端校验**B 端角色白名单**（`super_admin/admin/researcher/teacher/operator`）
—— 校验的是**角色身份**，不是权限码。不满足 → **拒绝登录**（`40306`），
**不静默降级为 h5**（静默降级会让"我登进来了但什么都点不了"变成一个查不出的问题）。

#### 6.5.3 最终设计（4 步）

| 步 | 做法 |
|---|---|
| 1 | **通道 = `user_sessions.platform`**（`'pc'` = 管理端，`'h5'` = C 端；admin 前端已在传 `"pc"`） |
| 2 | 登录：`platform='pc'` 时校验 B 端角色白名单 → 不满足则 `40306 该账号不是管理端账号` |
| 3 | `/admin/*` 加依赖 `require_admin_session`：`sid` → 查 `user_sessions` → 要求 `revoked_at IS NULL` **∧** `expires_at > now()` **∧** `platform='pc'` → 否则 `40306` |
| 4 | C 端登录不传 `platform`（恒 `'h5'`）→ **永远拿不到管理端会话** |

**★ 顺序：权限墙在前、会话墙在后。** 理由：两者**都是拒绝**，
**顺序对安全性零影响**，只影响返回值 —— 而"权限墙在前"能**保住既有 3 条用例的语义**
（它们用的是"完全没权限"的账号，理应继续拿到 `40301 没有操作权限`）。
真正要挡的那一种（**C 端会话 + 拿到了某个 admin 权限码**）两个条件都不满足 → 撞 `40306`。

#### 6.5.4 ★ 白拿的收益：会话校验**统一做，C 端也做**（2026-09-26 用户裁定）

现在 `current_user` **不查会话行** —— 它只解 token，然后查用户与权限
（`deps.py:96-118`）。⇒ **登出 / 撤销会话后，access token 仍有效到自然过期。**

**用户的裁定（原话）**：*"它和 §6.5 同族（『会话』和『token』要分别管理）。
如果首批不做，将来补的成本是『**改 C 端登录接口 + 迁移已有会话**』。"*
⇒ **首批决定：C 端也用会话墙。**

**落地方式（这比"只在 `/admin/*` 加依赖"更干净）**：把会话有效性放进 **`current_user` 本身** ——

| 层 | 判什么 | 覆盖 |
|---|---|---|
| `current_user`（统一） | `sid` → `user_sessions`：`revoked_at IS NULL` ∧ `expires_at > now()` | **所有**需登录接口（含 C 端）⇒ **登出即时生效** |
| `require_admin_session`（仅 `/admin/*`） | 在上一层的**基础之上**再加 `platform='pc'` | 管理端隔离 |

好处：**一处实现、两个诉求**（而不是两处各查一遍会话）；且 C 端从一开始就有"登出即时生效"，
不用等将来迁移会话。⚠️ 成本是**每个认证请求多一次按主键的 `SELECT`** ——
`user_sessions.id` 是主键，代价可控；若将来成为热点，正解是**加缓存**（而不是去掉这道校验）。

### 8.2 为什么不连"离线答题"一起做（4 条**具体**成本，不是"以后再说"）

| # | 成本 | 说明 |
|---|---|---|
| 1 | IndexedDB 队列 | 离线期间的作答要按序暂存，键是 `session_id` —— 这套还得处理"队列里已经有同一题的两份答案" |

| 4 | ★ **客户端判分不可信** | 离线时为了给即时反馈，只能客户端判分；但服务端接收补交时**必须重判** ⇒ 用户离线看到的"对/错"可能与最终结果不同。**这个不一致要不要展示、怎么展示，还没定** |
