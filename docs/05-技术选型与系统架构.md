# 05 · 技术选型与系统架构

## 1. 技术选型决策表

| 层次 | 选型 | 备选 | 决策理由 |
|---|---|---|---|
| **前端框架** | Next.js 14（App Router）+ TypeScript | Vue3 + Nuxt3 | 双端需求：移动端 H5 要 SEO（考点解析页收录）用 SSR，答题页要交互用 CSR，App Router 的 Server/Client Component 混用刚好匹配；生态与人才储备更足 |
| **UI / 样式** | Tailwind CSS 3 + shadcn/ui + Radix | Ant Design Mobile | Tailwind 对"移动优先 + 响应式"最直接；AntD Mobile 组件库视觉统一但定制成本高、包体大。管理端用 shadcn 的 Table/Form 组合 |
| **状态管理** | Zustand + TanStack Query | Redux Toolkit | TanStack Query 处理服务端状态（缓存/重试/失效）是答题场景刚需；Zustand 管本地轻状态（答题卡、离线队列） |
| **移动端** | PWA（next-pwa / Serwist） | 原生 APP / 小程序 | 一建考生是在职工地人群，**扫码即用**的转化率远高于装 APP；PWA 支持离线与桌面图标，开发成本 1/5 |
| **后端框架** | FastAPI（Python 3.12） | NestJS / Spring Boot | ① 题库导入、组卷、记忆曲线、统计都是**数据处理密集**，Python 生态（pandas/openpyxl/scikit-learn）优势明显；② 自动生成 OpenAPI 文档；③ 异步 IO 足以支撑 3000 QPS；④ 后续接 AI/LLM 答疑最顺 |
| **ORM** | SQLAlchemy 2.0（async）+ Alembic | Tortoise / 原生 SQL | 复杂抽题 SQL 用 `text()` 写原生；常规 CRUD 用 ORM。Alembic 管迁移 |
| **数据库** | PostgreSQL 16 | MySQL 8 | `JSONB`（答案结构/i18n/配置）、`TEXT[]`（标签）、GIN 索引、部分唯一索引、窗口函数——题库场景几乎每一条都用得上；MySQL 的 JSON 索引能力弱一档 |
| **缓存** | Redis 7 | — | Session / 限流 / 验证码 / 排行榜 ZSET / 热点题目 / 幂等键，一栈五用 |
| **搜索** | Meilisearch | Elasticsearch / Typesense | 中文分词开箱即用（内置 CJK）、单机 200MB 内存起步、建索引快、typo 容错好；ES 太重（JVM 2GB 起），一建 10 万题量用不上 |
| **对象存储** | MinIO（自建）/ S3 兼容 | 阿里云 OSS | 视频、讲义、导入文件、分享图。自建用 MinIO 免云费用，上云换 OSS 只改 endpoint |
| **任务队列** | Celery + Redis Broker（或 ARQ） | Kafka / RabbitMQ | 数据量不需要 Kafka。异步任务：转码、导入、报告生成、推送、统计刷新。ARQ 更轻但生态弱，选 Celery |
| **定时任务** | Celery Beat | APScheduler | 与队列同栈 |
| **视频** | FFmpeg 转 HLS（m3u8 + 多码率） | CDN + 云点播 | 自建省成本，移动端弱网靠 HLS 自适应码率；量大后切云点播 |
| **鉴权** | JWT（access）+ Refresh Token Rotation | Session | 前后端分离 + 多端（H5/小程序/后台）友好 |
| **部署** | Docker Compose → K8s（后期） | — | 一期单机 Compose 足够（日活 10 万以内）；容器化保证环境一致，后期平滑迁 K8s |
| **反向代理** | Nginx | Caddy | 限流、静态缓存、HTTPS、HLS 分片服务，Nginx 更成熟 |
| **监控** | Prometheus + Grafana + Loki | Sentry + 云监控 | 指标 + 日志 + 链路；错误追踪用 Sentry |
| **CI/CD** | GitHub Actions / GitLab CI | Jenkins | 构建镜像 → 推送 Registry → 服务器 `docker compose pull && up -d` |

### 1.1 为什么后端不用 NestJS/Spring Boot

不是它们不好，而是**这个业务的瓶颈在数据处理而不在并发**：

| 业务动作 | 用 Python | 用 Java/Node |
|---|---|---|
| 导入 1 万道题的 Excel，去重、清洗、写库 | pandas + openpyxl，200 行代码 | 需要 EasyExcel/POI 或多层抽象 |
| 组卷：按题型/难度/知识点/年份多约束抽题配比 | numpy 权重采样，天然表达 | 需要手写算法 |
| 题目质量分析：区分度、难度校正 | scipy 现有的 IRT 实现 | 需要自己实现 |
| 成绩预测、学习报告 | scikit-learn / pandas | 一般 |
| 后续 AI 答疑（RAG、向量检索） | 生态最全 | 一般 |

而后端并发：一建平台的峰值是**考前一周 + 查分日**，日活 10 万级别的 QPS 峰值约 1500–3000，FastAPI + 异步 + Redis 缓存 + 2~4 个 worker 完全够。

> **如果团队是 Java 强背景**，把 FastAPI 换成 Spring Boot 即可，其余架构（PG/Redis/Meili/MinIO/队列）完全不变。数据密集型的三个模块（导入管道、组卷、分析）可以用 Python 写独立 worker 服务，Java 主服务通过队列调用。这是最稳的折中。

## 3. 关键技术方案

### 3.1 移动端弱网与离线（这是核心体验）

一建考生常在工地、电梯、地铁里学习。**离线能力不是加分项，是必需项。**

```
用户答题 → 判断网络
  ├ 在线 → 直接 POST，成功则更新本地缓存
  └ 离线 → 写入 IndexedDB 队列 → 本地立即判分（题目答案已在创建练习时缓存到本地）
           UI 提示「已离线保存，联网后同步」→ 恢复网络后 Background Sync 顺序重放
```

**关键设计：创建练习时把该批题目的"答案+解析"一次性加密缓存到 IndexedDB。**

- 这样离线也能即时判分、看解析
- 缓存的是**该用户已开始作答的题目**，不是全库，防止批量抓题
- 缓存条目带 `session_id` 与过期时间（24 小时），过期自动清理
- 队列重放时用 `Idempotency-Key` 保证不重复计分

### 3.2 抽题算法（组卷）

```python
def compose_paper(rules: list[dict], subject_id: int) -> list[int]:
    """
    按规则组卷。每个 rule:
      {"type":"single","count":60,"score":1,"difficulty":[2,4],
       "kp_ids":[...],"year":None,"prefer_unused":True}
    策略：
      1. 先按 (type, difficulty, kp) 精确匹配
      2. 不足则放宽难度范围
      3. 仍不足则放宽知识点
      4. 记录"缺口"，返回给教研人工补题（不静默凑数）
    """
    result, shortfalls = [], []
    for rule in rules:
        picked = fulltext_filter(rule)          # 走 idx_questions_filter 索引
        if len(picked) < rule["count"]:
            picked = relax_difficulty(rule, picked)
        if len(picked) < rule["count"]:
            picked = relax_kp(rule, picked)
            shortfalls.append({"rule": rule, "need": rule["count"], "got": len(picked)})

        # 加权采样：优先选从未被用过的题，其次选使用次数少的，避免"考卷重复"
        weighted = weighted_sample(picked, weigh_by_usage, rule["count"])
        result.extend(weighted)
    return result, shortfalls
```

**自动组卷必须回传 `shortfalls`（缺口）。** 一个静默凑数的组卷器会让教研失去对卷面质量的掌控。

### 3.3 判分引擎

```python
def grade_objective(qtype: str, correct: list, user: list, score: float) -> tuple[float, bool]:
    if qtype in ("single", "judge"):
        ok = set(user) == set(correct)
        return (score if ok else 0.0), ok

    if qtype == "multiple":
        cor, usr = set(correct), set(user)
        if not usr:
            return 0.0, False
        if usr - cor:                     # 选了错误项 → 0 分
            return 0.0, False
        if usr == cor:                    # 全对
            return score, True
        # 漏选：按比例给分，最低 0.5 分（贴近真实考试规则）
        ratio = len(usr) / len(cor)
        partial = round(score * ratio, 1)
        return max(partial, 0.5), False

    if qtype == "fill":
        return (score if normalize(usr) == normalize(correct) else 0.0), False

    return 0.0, None                      # 主观题，走自评/人工
```

> **多选题的漏选给分规则必须可配置**（`app_configs.question.answer_rule`）。各地/各年份的判分细则会有差异，写死会出问题。

### 3.4 掌握度与薄弱点

- 每题作答 → 实时更新 `user_question_state.mastery` 与 `user_knowledge_stats`
- 薄弱点 = 该科目下 `mastery < 0.6 且 attempt_count >= 3` 的知识点，按 `(1 - mastery) × importance` 排序取 Top 10
- 归因：结合 `user_wrong_reasons` 的错因分布，输出"你在【成本管理】主要是概念不清，在【进度控制】主要是计算错误"

### 3.5 搜索（Meilisearch）

```python
# questions 索引配置
{
  "searchableAttributes": ["stem", "keywords", "analysis", "tags"],
  "filterableAttributes": ["subject_id", "chapter_id", "knowledge_point_id",
                            "type", "difficulty", "exam_year", "source_type", "status"],
  "sortableAttributes": ["exam_year", "difficulty", "created_at"],
  "rankingRules": ["words", "typo", "proximity", "attribute", "sort", "exactness"],
  "pagination": {"maxTotalHits": 10000}
}
```

同步策略：题目发布/更新时通过 Celery 任务增量推送到 Meilisearch；每日凌晨全量对账一次（比对 `updated_at`）。

### 3.6 缓存一致性

```
写路径：先写 DB → 提交事务 → 删除缓存（Cache-Aside + 删除而非更新）
读路径：查缓存 → 命中返回 → 未命中查 DB → 回写缓存（TTL 加随机抖动防雪崩）
```

- **绝不"先删缓存再写库"**：并发下会产生脏数据
- 热点 key（科目树、当前公告）加 30 分钟随机 TTL，防同时过期引发缓存雪崩
- 缓存穿透：查不到的 key 也缓存空值（TTL 60 秒）
- 缓存击穿：热点 key 用 Redis SETNX 加互斥锁，只放一个请求查库

## 4. 非功能性设计

### 4.1 安全

| 威胁 | 对策 |
|---|---|
| 密码泄露 | bcrypt（cost=12）+ 登录失败锁定 + 弱密码黑名单 |
| Token 盗用 | access 短时效（2h）+ refresh rotation + 设备绑定 + 异地登录告警 |
| 越权访问 | 接口级权限 + **数据范围**校验（教研只能改自己专业的题） |
| 答案泄露 | 未作答不下发答案；题目接口不含答案字段；管理端与 C 端 token 隔离 |
| 刷题/爬库 | Redis 令牌桶 + 行为风控（单用户 1 分钟超 300 题触发告警）+ 题干水印 |
| SQL 注入 | ORM 参数化；原生 SQL 一律用绑定参数，禁字符串拼接 |
| XSS | 富文本用 DOMPurify 白名单清洗；CSP header |
| CSRF | SameSite=Lax + 关键操作二次校验 |
| 短信轰炸 | 图形验证码前置 + 手机号/IP 双维度限流 + 异常告警 |
| 文件上传 | 类型白名单 + 大小限制 + 病毒扫描 + 存储与业务域隔离 |
| 支付安全 | 回调验签 + 白名单 IP + 幂等 + 金额二次核对 |
| 数据泄露 | 敏感字段加密存储、导出走审批并留痕、日志脱敏手机号 |
| 越权下载 | 播放/下载 URL 带时效签名（HMAC + 过期时间），有效期 5 分钟 |

### 4.2 可用性

| 项目 | 目标 |
|---|---|
| 可用性 | 99.9%（年停机 < 9 小时） |
| RPO（数据丢失容忍） | < 5 分钟 |
| RTO（恢复时间） | < 30 分钟 |
| 首屏（4G） | < 2.5s |
| 答题接口 P95 | < 150ms |

考前 7 天与查分日是流量峰值（约日常 10 倍），预案见 `docs/06-部署运维与安全方案.md`。

| 扩展方向 | 预留设计 |

| 多品类（二建、造价、消防） | `subjects.exam_level` 已区分；只需加数据 |
| 多租户 / 加盟商 | `user_roles.scope_type` 可扩展 `tenant`；表加 `tenant_id` 即可 |
| 直播课 | `lessons.type` 已有 `live`；需加 WebSocket 服务与 IM |
| AI 答疑 | `recommendations.rec_type` 可扩展；Ask 服务独立部署，通过队列对接 |
| 小程序 | 复用同一套 API；仅需引入微信登录与支付渠道 |
| 大数据分析 | 数据同步到 ClickHouse / Doris，报表层独立 |

## 6. 技术风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 一建真题版权 | **最高**，可能导致产品下架 | 只用授权/原创/公开来源；`source_license` 字段留痕；建立内容合规审查流程（详见 docs/07） |
| 视频带宽成本 | 高 | HLS 多码率 + CDN + 限制并发播放；讲义优先，能看文字不看视频 |
| 移动端兼容性（工地老旧安卓机） | 中 | 支持到 Android 7 / iOS 13；避免用最新 CSS 特性；降级方案（无 PWA 时按普通 H5 工作） |
| 组卷题目重复 | 中 | `weigh_by_usage` 优先选未用过的题；试卷发布后锁定题目快照 |
| 主观题评分争议 | 中 | 评分点公开透明 + 自评与人工双通道 + 申诉入口 |
| 高并发交卷 | 中 | 交卷走异步评分；Redis 队列削峰；幂等键防重复 |
| 团队数据分析能力 | 低 | 先用规则引擎（SM-2 + 阈值），不追求复杂模型；有数据后再上 ML |
